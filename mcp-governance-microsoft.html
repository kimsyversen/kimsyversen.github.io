The design

In shortKeep the company MCP server behind the gateway and limit managed clients to approved servers. With preview, add an Agent 365 admin view and optional blocking. Test preview features only in a sandbox. recommendation

DesignsReleased only is the target baseline. Use only confirmed released features; keep unverified automation out of production. With preview adds Agent 365 and tool threat protection, for a sandbox only.

Approval boundaries and cross-cutting guardrails

Keep one reviewed inventory, but translate it into each target's control. A server allowlist, an agent's tool allowlist, and a federated connector audience are different settings. Treat the target's actual policy as the effective control, and record exceptions and sync status. recommendation

  • Review capability changes. Re-review a server when its URL, authentication, permissions, or exposed tools change. Remove tools an agent does not need, and keep Foundry's allowed_tools list nonempty. An empty list permits all tools. V69 recommendation
  • Check coverage exceptions. GitHub's allow and deny lists do not block the built-in GitHub MCP server and do not apply to servers in custom agent profiles. Power Platform blocks MCP servers as a whole, not individual tools. Add separate controls for these gaps. V20 V21 V65 recommendation
  • Enforce identity and authorization at the service. Require authentication and authorize each request at the gateway and backend. Network allowlisting and a client approval prompt do not grant permission to read or change data. Microsoft says IP allowlisting does not replace authentication or authorization. V6 V8 V174 recommendation
  • Verify and audit the whole path. Test that an unapproved server, an unapproved tool, and an unauthorized identity are denied. Check that each policy target received the current inventory. Retain gateway logs and review connector activity in Purview where applicable. V3 V165 recommendation

Order of work

GoalFour steps, in this order.Build the baseline first. The pilot starts only after it. recommendation

  1. First. Inventory MCP use, put the approved list in a repository and build the pipeline that applies it.
  2. Next. Isolate the company MCP backends and require access through API Management.
  3. Then. Add endpoint application control, local server limits and outbound policy.
  4. Finally. Add monitoring, review exceptions and run the bypass tests on a schedule.

Preview pilot, after the baseline preview

  1. Scope. Pick a low-risk server with two read-only tools and one controlled write tool. Record owner, data class, sign-in and expected clients.
  2. Resource type. Create the AI Gateway on the new resource type in a supported region V45 V52. Confirm eligibility, the public front door, networking, policy features and licensing.
  3. Publish. Publish the server through the gateway. Set the backend credential or managed identity, authorization, policies and logging. Use the gateway URL it issues.
  4. Lock the backend. Make direct calls fail. Check the supported backend network design, because the new gateway has no private endpoints V47.
  5. Connect Agent 365. For the API Management integration, after named tenant-admin consent, connect the gateway and check that the server shows up. Review the permissions granted V40.
  6. Test blocking. For the API Management integration, test a server block, then a named tool on a supported tier with a static tool list. If tool blocking fails on the new resource type, treat that combination as unsupported.
  7. Threat protection. Turn it on in a user-token flow. Test Audit, Block and failure handling. Do not expect the same result for app-only workloads V54.
  8. Client policy. Apply the repository list to the managed client allowlists, Foundry and Copilot Studio through the pipeline. Add endpoint and outbound controls.
  9. Monitor. Watch gateway events, denied calls, admin changes and direct-connect attempts. Record blind spots and log retention.
  10. Gate promotion. Require accepted support terms, released features, incident playbooks and a rollback plan before leaving the sandbox V35.

Known gaps and what has not been tested

Bad news first Read these limits before relying on the design.

  1. No part of the design is tested in a tenant. Every expected result above is a target, not a result. This includes Agent 365 and Foundry against the new AI Gateway resource type.
  2. Built-in GitHub MCP server. Allow and deny lists cannot block it V21 V92. Two other switches are untested for it: the MCP servers in Copilot policy, which turns off all MCP V93, and Registry only V94, a public preview with weaker enforcement V95 V96. The design has no control for it. See the open questions.
  3. Microsoft 365 Copilot is set by hand. Agent and plugin access has no PowerShell or API option V171, so the pipeline cannot keep this target in step. unverified No page read says whether a custom connector can be created by API. Declarative agents that carry their own MCP server were not checked.
  4. Microsoft 365 Copilot connector status. inference Interpretation by AI: the federated connector pages read on 2026-11-11 carry no preview label for the connectors, so the page treats them as released. Confirm in the target tenant.
  5. Windows outbound block. It can block non-MCP traffic too, and name-based rules have limits with proxies and some VPN tunnels. V32 V34
  6. API Management tier availability. MCP features vary by tier. Confirm the target tier and release status before relying on a feature. V64 V80 V81

Fallback

GoalIf a preview feature changes, keep the released-only design running underneath. Use the preview controls in a sandbox only. recommendation

  1. Keep production MCP servers behind the released-only design, using only API Management features whose release status is confirmed.
  2. Switch off the preview integrations for the affected workloads.
  3. Keep client policy, backend isolation, least privilege and logging as they are.
  4. Check which capabilities remain before the switch. recommendation

Open questions

  1. 1

    Are preview features allowed at all?

    Choices: never, in a sandbox only, or later. Require released features for production. The proposed pipeline and cross-client enforcement still need validation.

  2. 2

    Which comes first: developer workstations or hosted agents?

    Workstations call for client rules and, on Windows, outbound limits. Hosted agents call for network isolation and data policies. Start where the more sensitive backends are. See the environment table.

  3. 3

    Is a default outbound block on managed Windows laptops acceptable?

    Decide before rollout. The effect on other traffic is in the gaps.

  4. 4

    Who reviews list changes and owns the pipeline?

    Name the reviewers of the repository, the pipeline owner and the person called when a target fails to update. Name who applies the list by hand in the Microsoft 365 admin center.

  5. 5

    Is the built-in GitHub MCP server acceptable on managed clients?

    The allow and deny lists cannot block it. Choices: accept it, turn off the MCP servers in Copilot policy (stops all servers), or limit it through GitHub account permissions. inference No source checked says whether that policy or Registry only covers the built-in server. Test both in a pilot.

  6. 6

    Who approves and reviews the Agent 365 consent?

    The consent lets the service write API policies. Name an approver and a reviewer. See the controls.

  7. 7

    What ends the pilot?

    Set the exit evidence now: terms accepted, features released, clients covered. Without it the pilot has no end. See the fallback.

  8. 8

    Does a gateway with no private endpoints fit the network rules?

    The new resource has no private endpoints. Check the rules before building. See the gaps.

  9. 9

    Which Agent 365 route will the pilot use?

    Choose the API Management gateway integration or the separate BYO server registration route. See the controls.
