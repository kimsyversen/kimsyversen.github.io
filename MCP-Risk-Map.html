The fourteen risks

Grouped from the OWASP MCP Top 10, the CoSAI MCP security paper and the specification's security guidance. The order and the grouping are interpretation by AI. [inference] OWASP's list is in beta and CoSAI's paper is marked draft, so both may change.

Scope: the 10 OWASP entries and 34 numbered CoSAI threats cited here. These source lists overlap. This map classifies individual control failures once using the boundaries below. An attack can contain several different failures. Coverage of these lists does not establish coverage of every possible MCP risk. Interpretation by AI. [inference]

Section roles: the map and zone table show risk locations; map markers open risk details and checks; the hidden Risks tab remains available to deep links; the product tab records implementation details. Evidence, sources and verdicts are recorded in MCP-Risk-Map.factcheck.md. Repeated risk IDs are cross-references, not additional risks.

Classification boundaries

Classify the failed control, not every consequence. Use the most specific boundary below. Split a chain into separate findings only when distinct controls failed. A finding outside these definitions remains unclassified pending review. These boundaries and tie-breaks are interpretation by AI. [inference]

  • M01 Server admission: unapproved server selection or registration. Inventory visibility belongs to M08; package identity deception to M02.
  • M02 Code provenance: malicious packages, dependencies, updates or look-alike software identities. Execution validation belongs to M03; tool metadata to M13.
  • M03 Execution boundaries: unsafe command construction, startup execution, file-path validation or process isolation. Package provenance belongs to M02; model instructions to M04.
  • M04 Model instruction boundaries: untrusted resource content or output treated as instructions. Tool definitions belong to M13; context disclosure to M10.
  • M05 Credential lifecycle: secret exposure, insecure storage, token theft or session replay. Granted scope belongs to M06; caller validation to M14.
  • M06 Granted privileges: valid permissions exceed the task. Bypassing an access check belongs to M14.
  • M07 Network destinations and origins: unsafe URL handling, SSRF, inbound exposure, CSRF or cross-origin checks. Channel integrity belongs to M12; caller identity to M14.
  • M08 Visibility: missing inventory, attribution, logging or monitoring. Server admission belongs to M01.
  • M09 Decision oversight: missing or ineffective human approval, or reliance on model judgment as the safety control. Specific command and access validators belong to M03 and M14.
  • M10 Data boundaries: over-sharing, retained context, tenant data isolation or data corruption without a more specific failed control. Credential, access and transport failures belong to M05, M14 and M12.
  • M11 Resource budgets: missing rate, size, recursion, workload or spending limits. Other transport defects belong to M12.
  • M12 Channel and message integrity: transport interception, tampering, descriptor handling or remaining protocol integrity defects. Network reach belongs to M07; authentication to M14; limits to M11.
  • M13 Tool definition integrity: poisoned descriptions, metadata or schemas. Executable packages belong to M02; returned content to M04.
  • M14 Identity and access enforcement: caller validation, audience checks, consent binding or authorization bypass. Excess valid privileges belong to M06; credential theft to M05.

    M01

    Unapproved MCP servers

    OWASP MCP09 · CoSAI #6

    In plain words: Without enforced restrictions, users can configure unapproved servers. An allowlist limits which servers can load within its documented scope.

    By default in Claude Code anyone can connect any MCP server. Anthropic reviews connectors before listing them in its Directory, but does not security-audit or manage any MCP server. So each developer decides what the agent can reach, unless policy limits it.

    Check
    • Is there an approved list of servers, and is it enforced?
    • Does the list cover both remote servers and local ones?
    • Is a server's name used as the control? Anthropic says the name is not a security control.
    How to set it

    Claude Code: use managed allowedMcpServers with allowManagedMcpServersOnly: true. For servers subject to the allowlist, URL entries require remote URL matches, and command entries require stdio command matches. Matching deny rules take precedence.

    managed-mcp.json restricts user-added servers, but an empty mcpServers does not disable every server: managed-settings servers, in-process SDK servers and explicitly permitted connectors or built-ins can still load. SDK servers skip these checks; some managed and built-in servers skip the allowlist. Review the vendor's exceptions for your session type.

    Codex: configure server identities under [mcp_servers.<name>] in managed requirements.toml. VS Code: use ChatAllowedMcpServers; review the selected harness and policy coverage.

    Typical findingsUnrestricted server configuration, required servers missing from the allowlist, user-assigned names used as identity checks. [inference]

    M02

    Tampered or malicious server code

    OWASP MCP04 · CoSAI #5, #25, #32

    In plain words: A local server is a program someone wrote. If it is malicious, it can act with the launching account's privileges unless isolation restricts it.

    A local server may be installed from a package or repository, or written locally. A tampered package, a bad update or a look-alike name brings malicious code in. Without adequate isolation, it can execute with the MCP client's privileges. No MCP-specific incident for this risk is cited here.

    Check
    • For server admission and command matching, see M01.
    • Who wrote each approved server, and how does it update? [inference]
    • Are server and package names checked against look-alikes before install? [inference]
    How to set it

    Claude Code matches serverCommand exactly but does not compare the env block. Matching a command does not verify the contents of its package or executable. [inference]

    Codex: the string form of command does not check args, cwd or env; the structured form checks the executable, argument count, order and matching rules. It still ignores cwd, env and env_vars.

    Typical findingsServers installed from any package, no review of updates, unpinned versions. [inference]

    M03

    Local servers run commands as the user

    OWASP MCP05 · CoSAI #21, #22, #31

    In plain words: A local server is started by a command. If the client executes a malicious command, attacker code runs within the configured execution environment.

    The MCP specification lists local server compromise as a risk: a malicious startup command in the client config, or a malicious payload in the server. The results it names are arbitrary code execution, no visibility and data exfiltration.

    OWASP lists command injection as MCP05: an agent builds and runs commands or code from untrusted input. This card covers execution and file-path validation failures. Instructions interpreted by the model sit under M04; compromised packages sit under M02.

    Check
    • Does your client ask before it runs a server's command, and show the whole command? The specification (2026-07-28) says a client with one-click local setup must.
    • Does your client sandbox local servers? The specification says clients should run them with minimal default privileges.
    • Is stdio used where possible? The specification says server authors should use stdio, or restrict HTTP with an auth token or unix sockets.
    • Do tools that build shell commands or code from model input validate that input first? [inference]

    Typical findingsOne-click setup that hides the command, servers started with no sandbox. [inference]

    M04

    Prompt injection through tool output

    OWASP MCP06 · CoSAI #4, #11

    In plain words: The agent reads text that tools bring back. If that text contains malicious instructions, the agent may follow them.

    A tool can read pages, tickets or files that someone else wrote. Malicious instructions, visible or hidden, can steer the agent. OWASP and CoSAI list this category. The Microsoft view cites an Invariant Labs research demonstration; no victim incident is verified here.

    Text inside a tool's own description or schema sits under M13.

    Check
    • Which servers read content you do not control (web, tickets, mail, shared files)? [inference]
    • Are untrusted reading tasks separated into sessions without tools that can write, send or run things? [inference]
    • For human approval controls, see M09. [inference]

    Typical findingsOne agent holding both a reader of outside text and a server that can send or change things. [inference]

    M05

    MCP tokens stolen or redirected

    OWASP MCP01 · CoSAI #16, #17, #19

    In plain words: A valid bearer token can authorize access within its scope. An attacker who intercepts it may be able to reuse it until it expires or is revoked.

    Mitiga (May 2026) showed an npm postinstall hook that edits ~/.claude.json and points an MCP server URL at an attacker's localhost proxy. Mitiga shows interception and reuse of an OAuth bearer token with Atlassian. Its article discusses refresh-token persistence but does not separately demonstrate capture of a refresh token.

    The chain requires local code execution through the npm installation. Mitiga describes a project SessionStart hook that restores the malicious endpoint; remediation must remove that persistence as well as repair the configuration and rotate credentials.

    Check
    • Do you watch ~/.claude.json and project MCP files for changed server URLs? Mitiga recommends this.
    • Is there a baseline of approved MCP endpoints, with an alert on new local proxies? Mitiga recommends this too.
    • After a suspected case, is the config fixed as well as the tokens rotated? Mitiga says rotating tokens alone is not enough.

    Typical findingsNo watch on MCP config files, overly long-lived credentials. [inference]

    M06

    Permissions wider than needed

    OWASP MCP02 · CoSAI #20

    In plain words: A key that opens many doors does more harm when stolen. Tokens and permissions should be as narrow as the task allows.

    A stolen token with wide scope reaches further than a narrow one. OWASP lists privilege escalation via scope creep as MCP02, and CoSAI lists excessive permissions and overexposure (#20).

    Check
    • Are permissions narrow? The specification recommends a progressive, least-privilege scope model. Token lifetime and storage belong to M05.
    • Does each server get only the access its job needs? [inference]
    • Who reviews a request for more access when a scope grows? [inference]

    Typical findingsBroad personal tokens in MCP config, servers with more access than their job needs. [inference]

    M07

    Local HTTP servers and URLs from servers

    CoSAI #26, #29, #30 · MCP specification: transports and security best practices

    In plain words: A server on your own computer can be reached by other programs, and sometimes by web pages. A server can also send your client to addresses it should not visit.

    An MCP server that listens on local HTTP can be reached by other local programs and, through DNS rebinding, by web pages. The specification also warns that a malicious server can supply URLs that point at internal addresses, such as 169.254.169.254.

    Check
    • Local HTTP servers: do they check the Origin header (must), bind to 127.0.0.1 rather than 0.0.0.0 (should) and require authentication (should)? Source: specification 2026-07-28.
    • For OAuth metadata discovery, does the client require HTTPS, restrict private and reserved destinations, and recheck redirect targets? The guidance recommends these checks for production, with explicit loopback exceptions for development. For server-side client deployments, operators should consider an egress proxy.
    • Does the client require HTTPS authorization URLs, allow HTTP only for loopback during local development, reject dangerous schemes such as javascript:, and avoid shell execution when opening URLs? The guidance requires these protections.

    Typical findingsA server left running on localhost with no token, bound to all interfaces. [inference]

    M08

    No audit trail or inventory

    OWASP MCP08 · CoSAI #15, #34

    In plain words: Without server inventories and suitable logs, it is hard to say which servers were used and what they did. [inference]

    OWASP lists missing audit and telemetry as MCP08. CoSAI adds invisible agent activity (#15) and lack of observability (#34). No MCP-specific incident for these risks is cited here.

    Check
    • Is there a list of servers in use and who runs them? [inference]
    • Can you see MCP use? Claude Code usage can be monitored with OpenTelemetry; OTEL_LOG_TOOL_DETAILS=1 is the variable the docs name for tool details.
    • Can you tell afterwards which tool calls an agent made? [inference]

    Typical findingsNo inventory, no usage logs. [inference]

    M09

    Weak approval and over-trust in the model

    CoSAI #7, #9, #13

    In plain words: People may approve tool calls without reading them, or a tool may trust the model to behave. Either way, a risky action can go ahead unchecked. [inference]

    CoSAI lists insecure human-in-the-loop checks, approval fatigue and overreliance on the model as MCP threats. The specification says there should always be a human in the loop who can deny tool invocations. This map assigns it a separate CoSAI home; see the mapping rules below. [inference]

    Check
    • Which tools can write, send or delete, and does each one ask a person first? [inference]
    • Are prompts few enough to be read, or does everyone approve everything? [inference]
    • Does any server leave safety to the model instead of checking input itself? [inference]

    Typical findingsAuto-approve switched on for tools that write or send. Tools that accept any input because the model is expected to behave. [inference]

    M10

    Over-sharing and shared servers that mix users

    OWASP MCP10 · CoSAI #10, #24

    In plain words: Data can be disclosed or corrupted through over-sharing, retained context or weak tenant isolation. Credential theft belongs to M05; failed identity or access checks belong to M14. [inference]

    MCP calls send data to the selected server. Local calls can stay on the machine; external disclosure depends on the server, host and model deployment.

    OWASP lists context injection and over-sharing as MCP10. CoSAI adds improper multitenancy (#10), meaning weak isolation between tenants or users, and data exfiltration and corruption (#24). No MCP-specific incident for these risks is cited here.

    Check
    • Has someone decided what may be sent to remote servers? [inference]
    • Does the server serve more than one user or team? [inference]
    • Are each user's data and context kept apart, with retention and deletion rules? [inference]
    • For shared identities and access enforcement, see M14. [inference]

    Typical findingsUnnecessary data sent to remote servers. Shared context or cache data exposed to another user. Missing controls on data modification. [inference]

    M11

    Runaway cost and overload

    CoSAI #14, #33

    In plain words: An agent or an attacker can make so many calls that costs or load get out of hand. [inference]

    CoSAI lists resource exhaustion and denial of wallet, and missing payload limits. The specification says servers must rate limit tool invocations. This map assigns it a separate CoSAI home; see the mapping rules below. [inference]

    Check
    • Is there a spending or rate limit on the model and on the API keys that agents use? [inference]
    • Do servers limit request size and call rate? [inference]
    • Who is alerted when use jumps? [inference]

    Typical findingsNo spending cap on agent keys. No limit on payload size or call rate. [inference]

    M12

    Weak protocol and transport protections

    CoSAI #12, #23, #27, #28

    In plain words: Traffic between MCP components can be read or changed if transport integrity fails. Stolen-token or session replay belongs to M05. [inference]

    CoSAI lists man-in-the-middle attacks, missing integrity checks, protocol security gaps and insecure handling of transport descriptors such as stdio. This map assigns transport integrity to M12 and HTTP origin or destination checks to M07. [inference]

    Check
    • Do remote servers use HTTPS, with certificates checked? [inference]
    • Is there any integrity check on messages beyond the transport? [inference]
    • Can another process read or write the stdio pipes of a local server? [inference]

    Typical findingsRemote servers on plain HTTP. Certificate checks switched off. [inference]

    M13

    Poisoned tool descriptions and schemas

    OWASP MCP03 · CoSAI #2, #3

    In plain words: A tool's name, description and parameters are text the model reads. If someone alters them, the model can be steered before any tool is called.

    OWASP defines tool poisoning as an adversary compromising the tools, plugins or their outputs that a model depends on. CoSAI lists tool poisoning (#2), altered tool metadata or descriptors, and full schema poisoning (#3).

    This page keeps poisoned outputs under M04 and uses M13 for the tool's own description and schema. [inference]

    Check
    • When a server is approved, does a person read each tool's description and schema? [inference]
    • Does the client ask again when a server's tool list changes? [inference]
    • Can a server change its tool descriptions without a version change you control? [inference]

    Typical findingsTool descriptions never reviewed. Servers that can change their tools after approval. [inference]

    M14

    Weak authentication and authorization

    OWASP MCP07 · CoSAI #1, #8, #18

    In plain words: Servers and clients must check who is calling and what that caller may do. If they do not, one party can act as another.

    OWASP lists insufficient authentication and authorization as MCP07. CoSAI adds identity spoofing (#1), privilege escalation through authentication or authorization bypass (#8) and weak or pass-through authentication (#18).

    The specification forbids token passthrough: an MCP server must not accept tokens that were not issued for it. It also warns that a proxy server with a static client ID can be abused (confused deputy).

    Check
    • Does each server verify who the caller is, not only that a token exists? [inference]
    • Do servers you or a supplier run refuse tokens not issued for them?
    • Proxy servers with a static client ID: per-client consent, exact redirect_uri match and single-use OAuth state.

    Typical findingsServers that forward whatever token they receive. Servers that accept calls without checking the caller. [inference]
