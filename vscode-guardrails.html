Which VS Code safeguards stop an AI agent?

In VS Code editor chat with the Copilot harness, Workspace Trust controls whether agents are enabled in the workspace. Approval rules determine when you are asked to let a tool run. The agent sandbox limits access to files and network destinations for the operations it covers.

Approval and sandboxing

Approval

“Can this action run without asking for confirmation?”

A one-time approval covers the current request. A saved approval can cover later requests within its scope.

Sandbox

“Which resources can this covered process access when it runs?”

Approving a command leaves its sandbox restrictions in place. If a sandboxed operation needs to retry outside the sandbox, that retry requires a separate approval.

This simulator runs no commands or tools. It assumes built-in tools on supported local macOS or Linux with Bash, the project as the working directory, default approval, sandbox path and network rules except where modeled, and no saved approvals or managed policy. For blocked commands, it models a one-time request to run outside the sandbox. VS Code can also offer access to a specific path so a command can retry inside the sandbox.

In a trusted workspace, the MCP example assumes Copilot starts a local stdio server from the project’s .mcp.json under the selected sandbox setting, with chat.agent.sandbox.mcpServers at its default. Startup is separate from tool approval. Server connectivity and per-server sandboxing are outside this example.

Six steps the VS Code docs recommend

  1. Review a project before trusting it.
  2. Confirm the session’s workspace and execution environment.
  3. Choose an appropriate permission level.
  4. Restrict command access and verify it. Run /sandbox policy to check the execution machine and effective restrictions.
  5. Limit tools and credentials to the task.
  6. Review changes before integrating them.

Step names come from Recommended security baseline.
