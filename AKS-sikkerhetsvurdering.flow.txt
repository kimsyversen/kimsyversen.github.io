TITLE: How a request gets into AKS

Flow description:
Two kinds of request reach a cluster. A change to the cluster goes to the
Kubernetes API server. It must reach the server over the network, prove who it
is, be allowed to do what it asks, and pass the admission rules. Then it is
stored in etcd, and the scheduler and kubelet start the pod on a node. The
audit log is written along the way. A user's request to an app goes over the
network: Azure load balancer, ingress controller or Gateway, Service, the
NetworkPolicy for the pod, and then the pod. Traffic out of the pod passes the
outbound rules. Calls to Azure services use workload identity.

[stop] marks a step where the request can be stopped.
Owners in brackets are typical. [inference]
