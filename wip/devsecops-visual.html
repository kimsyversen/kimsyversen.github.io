Governance activities

Delivery phase

Secure development activities

01

Plan

Set the direction

Governance

Classify

Name the risk owner, agree the security level, and record data scope, DPIA need and initial risks.

Risks

No named risk owner
“Roles, responsibilities, and authorities related to cybersecurity risk management are established, communicated, understood, and enforced.”
NIST CSF 2.0 · GV.RR-02 ↗

Secure development

Security requirements

Set scope, acceptance criteria, security and privacy requirements, and likely threats.

Risks

Sensitive data left out of scope
“protection requirements concerning confidentiality, integrity, availability, and authenticity of all data assets”
OWASP A06 · Requirements and Resource Management ↗
02

Design

Shape the solution

Governance

Choose concept

Compare options for architecture and supplier risk. Record the security case, expected residual risk, plan and budget.

Risks

Risk response left undefined
“Strategic direction that describes appropriate risk response options is established and communicated.”
NIST CSF 2.0 · GV.RM-04 ↗

Secure development

Threat modeling

Model threats across data flows and integrations. Turn mitigations into owned, testable requirements.

Risks

Abuse paths left open
“Threat modeling is a structured activity for identifying, evaluating, and managing system threats, architectural design flaws, and recommended security mitigations.”
OWASP SAMM · Threat Modeling ↗
03

Code

Build to the standard

Governance

Ready to build

Confirm the threat model, security backlog, delivery environment, pipeline checks and team ownership are ready.

Risks

Development starts without security requirements
“Identify and document all security requirements for organization-developed software to meet, and maintain the requirements over time.”
NIST SSDF 1.1 · PO.1.2 ↗

Secure development

Secure coding and review

Use secure coding standards, review changes, protect secrets and assess dependencies.

Risks

Credentials exposed in code
“The product contains hard-coded credentials, such as a password or cryptographic key.”
MITRE CWE-798 · Hard-coded Credentials ↗
04

Build

Package trusted inputs

Governance

Track evidence

Track whether security activities are complete. Keep findings, owners and due dates visible.

Risks

Security findings go untracked
“Record and track all security defects in a defined location.”
OWASP SAMM · Defect Tracking ↗

Secure development

Build traceability

Package from trusted inputs and keep the artifact traceable to its source and dependencies.

Risks

Build output tampered with
“An adversary introduces an unauthorized change to a build output through tampering of the build process”
SLSA 1.2 · Build Process Threats ↗
05

Test

Verify the controls

Governance

Review test evidence

Review test evidence against the agreed security requirements and follow unresolved findings to closure.

Risks

Security sign-off lacks test evidence
“consider the passing of security tests as part of merge requirements before allowing new code to enter the main code base.”
OWASP SAMM · Control Verification ↗

Secure development

Security testing

Check functionality, quality and security. Scan code, packages, secrets and infrastructure configuration.

Risks

Broken controls go unnoticed
“ensure that the implemented security controls operate as expected and satisfy the project’s stated security requirements”
OWASP SAMM · Requirements-driven Testing ↗
06

Release

Approve the version

Governance

Production go / no-go

Require verified controls, tested recovery and monitoring. Close critical and high findings or get the system owner’s explicit risk acceptance.

Risks

Accepted risk lacks stakeholder review
“all relevant stakeholders have a solid understanding of the imposed risk.”
OWASP SAMM · Defect Tracking ↗

Secure development

Release verification

Approve a verified, traceable software version after required checks pass.

Risks

A substituted artifact ships
“SLSA Build L2 covers tampering of the artifact or provenance after the build.”
SLSA 1.2 · Verifying Artifacts ↗
07

Deploy

Deliver with guardrails

Governance

Controlled promotion

Promote only the approved release and confirm the rollout is understood and reversible.

Risks

Unapproved changes reach production
“Implement approved configuration-controlled changes to the system”
NIST SP 800-53 Rev. 5 · CM-3 ↗

Secure development

Rollout and rollback

Use hardened settings and least-privilege access. Verify the rollout and support rollback.

Risks

Insecure settings go live
“missing appropriate security hardening across any part of the application stack or improperly configured permissions on cloud services”
OWASP A02 · Security Misconfiguration ↗
08

Operate

Run the service

Governance

Handover

Transfer operations and open actions with named owners, dates and the evidence needed to continue.

Risks

Open actions lose ownership at handover
“Roles, responsibilities, and authorities related to cybersecurity risk management are established, communicated, understood, and enforced.”
NIST CSF 2.0 · GV.RR-02 ↗

Secure development

Service maintenance

Maintain reliability, patch vulnerabilities, manage access and backups, and respond to incidents.

Risks

Known flaws stay exploitable
“Help ensure that vulnerabilities are remediated in accordance with risk to reduce the window of opportunity for attackers.”
NIST SSDF 1.1 · RV.2 ↗
09

Monitor

Learn from live signals

Governance

Measure: Improve

Review risk, overdue actions, vulnerability age, tested requirements and recovery results on a set cadence.

Risks

Overdue fixes go unreported
“centrally monitor and regularly report on SLA breaches.”
OWASP SAMM · Defect Tracking ↗

Secure development

Detection and alerting

Track service health, performance, user experience and security events. Alert on suspicious activity or change.

Risks

Attacks go undetected
“Without logging and monitoring, attacks and breaches cannot be detected”
OWASP A09 · Security Logging and Alerting Failures ↗
10

Retire

Close the lifecycle

Governance

Closeout: Confirm

Assign closure ownership and confirm remaining access and data obligations are addressed.

Risks

Retention obligations left unresolved
“You have retention requirements for data, and you destroy backups in a timely manner after the relevant retention period ends”
OWASP SAMM · Data Protection ↗

Secure development

Secure decommissioning

Decommission the service, revoke credentials and access, and handle data under retention requirements.

Risks

Old credentials still work
“When secrets are no longer required or potentially compromised, you must securely revoke them to restrict access.”
OWASP · Secrets Revocation ↗
Data remains recoverable
“Media sanitization refers to a process that renders access to target data on the media infeasible for a given level of effort.”
NIST SP 800-88 Rev. 2 · Media Sanitization ↗

↰Monitoring, incidents, changes and new vulnerabilities can send work back to planning.
