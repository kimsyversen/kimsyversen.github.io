How we govern MCP servers

GoalKeep one approved list in Git and distribute it automatically. Verify each route before allowing use. recommendation

Answer recommendation

Keep one approved MCP list in Git, and publish it by pull request into each technology's own control: the GitHub settings file for VS Code and Copilot, the Agent 365 registry or gateway for agents, data policies for Copilot Studio, Azure Policy for Foundry, and the network firewall for remote servers.

No single control covers every agent, so combine these, restrict direct API access with permissions at the source, and accept that most of these are previews that are untested in our tenant (see the route table).

    Submit a pull request with the owner, data, tools and risk tier. Record the approval or rejection.

  2. Publish the approved list

    Trigger distribution on merge. Record the policy version and result for each destination.

  3. Check the outcome

    Record discovery, applied configuration and verified enforcement separately. Complete any required administrator step.

  4. Enable and monitor

    Enable only tested routes. On incident, block access and verify revocation.

Risk tiers recommendation

Apply the highest applicable tier. Assess who operates the server separately from whether the endpoint is public. Use the action policy below for all permitted write and outbound tools.

  1. 1Read-only, internal, no sensitive dataInternal case searchAutomate checklist checks. Record approval in the pull request.
  2. 2Read-only, sensitive dataHR or finance readsSecurity and data owner
  3. 3Can change data or call outCreate tickets, send mail, deploySecurity and data owner approve publication. Apply the action policy at run time.
  4. 4Third-party operated or untrusted codeCommunity MCP serversDefault deny. A recorded exception must still meet the action policy.

Approval for tools and actions recommendation

Before publication
Review the endpoint, tool version, schema, data and permissions in the pull request. Security and the data owner approve tier 2 and tier 3 tools. Tier 4 also needs an exception.
For each call
Check that the caller may use this server, tool and resource. Apply access checks independently of the model.
For a write or outbound action
Require an authorized request or approved trigger. Require human approval for high-impact actions and actions outside an approved rule. A rules service may approve only explicitly approved low-risk actions, bounded by tool, permitted inputs, target and data. Deny if the required approval is absent.
For execution
Use a separate, narrowly scoped identity to execute an approved action. Record the approval and outcome.

The target state, as part of the governance

GoalShow how the pieces fit. One policy in Git, enforced by each platform, with work access from a managed desktop. recommendation

Answer recommendation

The target state is the same approved list, enforced in layers. Git holds the policy. Each platform enforces it with its own control. Consultants work from a managed desktop. Agents get their own identity, start read-only and need approval for high-impact actions. Logs and revocation close the loop.

  1. 1

    Apply one policy through each platform's own controls

    Verify where each control applies before enabling a route. Compare the routes.

  2. 2

    Allow only approved MCP servers and tools

    Start from default deny where supported. Test the exceptions and block or restrict alternate paths. Review and publish the approved list.

  3. 3

    Keep code and sensitive data on managed devices

    Give consultants on personal laptops a managed cloud desktop for work. Set up identity and device access.

  4. 4

    Give agents their own identity and least privilege

    Start with read-only access. Require human approval for high-impact actions. Use rules only for explicitly approved, bounded low-risk actions. Read the action policy.

  5. 5

    Manage policy changes in Git

    Require an approved pull request, publish the list automatically and verify the deployed policy. Follow the publication workflow.

All five points describe the proposed design.

Monitor and stop an agent

RunbookUse these steps for the affected route. recommendation

  1. Find the affected calls

    Use the tool-call record to identify the caller, route, tool, resource and decision.

  2. Contain the route

    Disable the agent and block the affected client or gateway route. Use the route matrix to locate other paths.

  3. Revoke at the source

    Remove tool or backend permissions and update the approved list in Git. Record each change.

  4. Verify the stop

    Retry from an existing agent and any permitted alternate path. Confirm denial and correlate the events before restoring access.

Open questions · For the owners

Open questions

  1. 1

    Is Git the one source of the approved MCP list?

    Every route then takes its entries from one reviewed file. Without it, each platform keeps its own list and the lists drift. See how the list is governed.

  2. 2

    Which routes do we enable?

    Enable only the routes that fit our needs. Keep the rest disabled. The route table shows what each route can and cannot do.

  3. 3

    Who owns the list, and who approves tiers 2 and 3?

    Name an owner for the list and for each server. Security and the data owner approve tiers 2 and 3. See the risk tiers.

  4. 4

    Do we accept preview controls?

    The watchlist names every control that its vendor labels preview. Decide whether we use them, and who re-checks them each month. See the preview watchlist.
