MCP Governance in a Microsoft ecosystem

A proposed design for governing MCP servers across GitHub Copilot, VS Code, Foundry and Copilot Studio. A Git repository holds the approved list, a pipeline applies it, and a gateway is the only way to reach the company MCP server. Select Released only or With preview. Nothing is built or tested yet.

The design

In shortMake the backend reachable only through the gateway (Objective A, not yet tested). Limit client servers to the approved list (Objective B). The repository list and pipeline apply Objective B; backend isolation for Objective A is separate. With preview, the design adds an admin view and optional block. Backend isolation remains Objective A. recommendation

ObjectivesA: the backend takes calls only from the gateway. B: clients can reach only approved servers.

DesignsReleased only is the baseline and uses no feature labelled preview. With preview adds Agent 365 and tool threat protection, for a sandbox only.

Order of work

GoalFour steps, in this order.Build the baseline first. The pilot starts only after it. recommendation

  1. First. Inventory MCP use, put the approved list in a repository and build the pipeline that applies it.
  2. Next. Isolate the company MCP backends and require access through API Management.
  3. Then. Add endpoint application control, local server limits and outbound policy.
  4. Finally. Add monitoring, review exceptions and run the bypass tests on a schedule.

Preview pilot, after the baseline preview

  1. Scope. Pick a low-risk server with two read-only tools and one controlled write tool. Record owner, data class, sign-in and expected clients.
  2. Resource type. Create the AI Gateway on the new resource type in a supported region V45 V52. Confirm eligibility, the public front door, networking, policy features and licensing.
  3. Publish. Publish the server through the gateway. Set the backend credential or managed identity, authorization, policies and logging. Use the gateway URL it gives you.
  4. Lock the backend. Make direct calls fail. Check the supported backend network design, because the new gateway has no private endpoints V47.
  5. Connect Agent 365. For the API Management integration, after named tenant-admin consent, connect the gateway and check that the server shows up. Review the permissions granted V40.
  6. Test blocking. For the API Management integration, test a server block, then a named tool on a supported tier with a static tool list. If tool blocking fails on the new resource type, treat that combination as unsupported.
  7. Threat protection. Turn it on in a user-token flow. Test Audit, Block and failure handling. Do not expect the same result for app-only workloads V54.
  8. Client policy. Apply the repository list to the managed client allowlists, Foundry and Copilot Studio through the pipeline. Add endpoint and outbound controls.
  9. Monitor. Watch gateway events, denied calls, admin changes and direct-connect attempts. Record blind spots and log retention.
  10. Gate promotion. Require accepted support terms, released features, incident playbooks and a rollback plan before leaving the sandbox V35.

Known gaps and what has not been tested

Bad news first Read these limits before you rely on the design.

  1. Nothing is tested in our tenant. Every expected result above is a target, not a result.
  2. GitHub exemptions. Custom agent profiles and the built-in GitHub server are outside the allowlist, and coverage varies by environment. V20 V21 V22
  3. GitHub cloud agent firewall. It does not directly control MCP server processes. Do not treat it as control of the MCP server itself. V23
  4. Foundry and Copilot Studio. The sources show network isolation, a tool list per agent and blocking a whole MCP server. V24 V65 V69 Blocking one chosen external MCP URL in either was not found in the sources checked on 2026-11-08, so the design does not rely on it.
  5. Power Platform API gap. ACP supports MCP connectors for server-level blocks V65, but the programmatic tutorial has no MCP-specific example V66. Confirm that the target environment and API expose the server before automating this policy. Custom and HTTP connector types aren't supported V78. Build and test one target at a time.
  6. Drift. A change made by hand in a target is not in the repository. The pipeline must overwrite it or raise an alert. recommendation
  7. Local stdio servers. The client starts a local server as a subprocess V28. The stdio transport uses standard input and standard output V89. Apply client and endpoint controls.
  8. Unmanaged workstations. Client rules are not assumed to apply there. Objective A relies on the backend refusing everyone but the gateway. recommendation
  9. Endpoint outbound block. It stops all traffic that matches no rule, not only MCP, and rules by name have limits with proxies and some VPN tunnels. V32 V34
  10. Feature release status. Microsoft announced general availability of API Management MCP governance in Nov 2025 V80 V81. Management features vary by tier V64. Confirm the tier you use.

Added with preview preview

  1. Preview terms. Microsoft states preview features are not meant for production use and may have restricted functionality. Use a sandbox. V35
  2. Resource migration. The AI Gateway resource type is changing and the older tier is permanently removed after the 15 Jan 2027 retirement date. V45 V46 V84
  3. Network limits. No private endpoints; the virtual network and subnet cannot change after creation. Check network and data-location rules first. V47 V48 V52
  4. Agent 365 BYO coverage. The route requires a publicly accessible server endpoint V88. It supports four client surfaces; Foundry and Microsoft 365 declarative agents aren't supported V43. Individual-tool blocking for BYO servers is planned, not available yet V86.
  5. Other preview routes. In the separate API Management integration, v2 tiers lack tool-level access control V42. Foundry gateway routing covers only new MCP tools created in the portal without managed OAuth V60.
  6. API Management integration does not force use. Agent 365 does not automatically route agents through a customer-hosted gateway. Configure agents to use the gateway endpoint, and make the backend refuse direct calls. V10
  7. Threat protection needs a user token. App-only calls are not supported, a license is needed, and a denial after the call cannot undo it. V53 V54 V57 V59
  8. Keep the Agent 365 routes separate. The API Management integration discovers servers registered with the connected gateway V36. BYO servers use a separate developer registration and admin approval flow V85 V87. Do not treat either route as a pipeline sync.
  9. Consent scope. The Agent 365 consent lets the service write API-scoped policies. Review it before granting. V40
  10. Shared backend credential. With a shared backend connection, authorized callers use that connection's permissions. Scope upstream credentials narrowly. V79
  11. Optional outbound filter. The Global Secure Access MCP firewall carries the preview label and sees remote servers only. V29 V31
  12. New resource type untested. We have not tested Agent 365 or Foundry against the new resource type. Test it in your tenant.

Fallback

GoalIf a preview feature changes, keep the released-only design running underneath. Use the preview controls in a sandbox only. recommendation

  1. Keep production MCP servers behind the released-only design, using only API Management features whose release status we have confirmed.
  2. Switch off the preview integrations for the affected workloads.
  3. Keep client policy, backend isolation, least privilege and logging as they are.
  4. Check which capabilities remain before the switch. recommendation

Open questions

  1. 1

    Do we allow preview features at all?

    Choices: never, in a sandbox only, or later. The released-only design works without preview.

  2. 2

    Which comes first: developer workstations or hosted agents?

    Workstations call for client rules and outbound limits. Hosted agents call for network isolation and data policies. Start where the more sensitive backends are. See the environment table.

  3. 3

    Do we accept an outbound block on managed laptops?

    Decide before rollout. The effect on other traffic is in the gaps.

  4. 4

    Who reviews list changes and owns the pipeline?

    Name the reviewers of the repository, the pipeline owner and the person called when a target fails to update.

  5. 5

    Who approves and reviews the Agent 365 consent?

    The consent lets the service write API policies. Name an approver and a reviewer. See the controls.

  6. 6

    What ends the pilot?

    Set the exit evidence now: terms accepted, features released, clients covered. Without it the pilot has no end. See the fallback.

  7. 7

    Does a gateway with no private endpoints fit our network rules?

    The new resource has no private endpoints. Check the rules before building. See the gaps.

  8. 8

    Which Agent 365 route will the pilot use?

    Choose the API Management gateway integration or the separate BYO server registration route. See the controls.
