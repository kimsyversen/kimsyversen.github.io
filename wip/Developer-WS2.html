Intune and MCP

Only approved MCP servers must run on a managed developer laptop.

A change from the approved state must show up and be put back.

Scope
Windows and macOS laptops managed by Intune, with GitHub Copilot in VS Code as the only MCP client
Status
Nothing tested in a real tenant
Basis
Vendor documentation, checked 2026-11-06

The answer

The design must be: GitHub Copilot in VS Code is the only MCP client that runs, VS Code must carry a managed MCP server list, and Intune must deliver it and put it back when it changes.

Intune has no MCP policy of its own. No Intune page read for this work names one. [inference]

The VS Code docs name Intune for the imported policy templates on Windows and for macOS profiles. V1 V48

VS Code has three MCP policies: an allowlist, a denylist and a managed-only switch. Deny wins. A policy value overrides the setting at every level. V2 V3 V4 V5

GitHub documents OS-level delivery for Copilot. The page does not name Intune, so the Intune route for that is an inference. [inference] V8

Intune can deliver App Control for Business policies to Windows devices. They restrict which apps run, so code runs only if the policy says so. V39 V40 V41

Windows only: an App Control policy that lists VS Code can keep another MCP client from running. It can also stop a local server that is its own program file. No source names MCP for this. [inference] V40

Defender file indicators can block a file on macOS. Blocking prevents the file from being read, written or executed. On macOS they cover Mach-O executables, POSIX shell scripts and AppleScript files. V42 V43 V44

On macOS, a file indicator can block a known unapproved client program or server script by its hash. That is a deny list, so a file not on the list is not stopped. No source names MCP for this. [inference] V44

App Control does not control scripts run through an unenlightened script host, such as many third-party Java or Python engines. A policy that allows such a host implicitly allows all scripts run through it. V45 V46

If node or python is such a host, a local server that it runs from a script file is not stopped on Windows while the policy allows it. Leaving it out of the policy also stops every approved server that needs it. On macOS the script is stopped only if it is on the deny list. [inference]

With VS Code as the only client, its managed list covers the local servers it starts. The open case is another client on the laptop, or another copy of VS Code that does not read the policy. [inference] V5

VS Code on every laptop must be a version whose reference page lists the three MCP policies.

If another MCP client is found on a laptop, a script must read its MCP file and flag any server that is not approved. That detects a server. It does not stop one.

Rollout

  1. VS Code and every other MCP-capable client on developer laptops must be listed first, from Defender discovery and from the software inventory.
  2. One approved server list must live in a repository, and the VS Code policy values must be written from it.
  3. A pilot group must get the Windows ADMX policy and the macOS profile first. VS Code must be tested with an approved and a blocked server.
  4. A client other than VS Code must be removed. On Windows an App Control policy must block it. On macOS a file indicator must block it by hash.
  5. Each laptop group must be assigned node and python as allowed or not allowed in its App Control policy, because allowing one allows every script it runs.
  6. Approved remote servers must be the only MCP destinations allowed through the firewall policy or Global Secure Access.
  7. Defender discovery must be compared with the approved list every week, and every difference must be explained or fixed.
  8. A laptop whose VS Code policy has changed must be found, and the approved policy must be put back.
  9. Nothing here must be called done until it has been tested in a real tenant.
