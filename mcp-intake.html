MCP server intake

A process to decide whether an MCP server may be used, and to decide again when it changes. It builds on enterprise controls.

MCP Security: enterprise controls MCP governance on Microsoft: controls

Start here

Passing intake lowers risk. It does not prove that a server is safe. inference

Quote
  • no check proves what a server will do. MCP docs: local server security

If you can only do ten things, do these.

  • H1 Publisher is identified
  • H2 It is the package the vendor means
  • H8 Not reported as malicious
  • A1 Exact version
  • D1 Isolated and disposable
  • D2 Whole surface captured and hashed
  • G3 Approver is not the requester
  • E2 Allowlist matches URL or command
  • W1 Definition drift
  • W2 New advisories

Process

Nine stages run in order. A failed gate stops the server there. Nothing from the server runs before Sandbox.

  1. 1RequestSay what is wanted
  2. 2ScreenJudge publisher and need
  3. 3PinFetch and fix the bytes
  4. 4ScanTraditional scanners
  5. 5ReviewMCP code and design
  6. 6SandboxRun it where it cannot hurt
  7. 7DecideApprove, limit or reject
  8. 8ReleaseMake only that copy runnable
  9. 9WatchDetect change, revoke

1. Request

Record what is asked for, so the later stages have something to test against.

What runs
Nothing from the server.
Inputs
  • Purpose and named owner
  • Link to the vendor's own documentation
  • Exact version, image digest or URL
  • Transport: local process or HTTP
  • Data it will reach
  • Tools wanted
  • Credentials and scopes
Steps
  1. Look in the approved catalog first. If an approved server covers the need, use it.
  2. Install nothing.
Output
A request record.

Gate Every input is filled in and an owner has accepted the role.

On a change Compare the new request with the approval record and write down what differs.

  • A local server is downloaded code that runs under your user account.
    Quote
    • When you run an MCP server locally, you download code from the internet and run it as a child process of your user account. MCP docs: local server security
  • Which tools a server lists can depend on the access it is given, so the requested scopes belong in the request.
    Quote
    • The set MAY vary by the authorization presented on the request MCP specification: tools

Checks

No checks of its own. The gate is the condition.

2. Screen

Reject bad candidates before anything is downloaded, and set the risk tier.

What runs
Nothing from the server. This is desk work.
Inputs
  • Request record
  • Publisher, repository and registry pages
  • Malicious package reports
Steps
  1. Run the hygiene checks.
  2. Give the server a provisional risk tier.
  3. Stop at the first check marked Block that fails.
Output
Go or stop, with a provisional tier.

Gate No blocking hygiene check has failed.

On a change Repeat for the new version: publisher, ownership, license, age and malicious reports can all differ.

  • A registry listing does not show that a server is safe.
    Quote
    • A listing on a registry is not an endorsement. MCP docs: local server security
  • Trusting a publisher does not show that every tool result is safe.
    Quote
    • Trusting a publisher or connecting a server doesn't establish that every tool result is safe. VS Code: agent security
  • Stars and download counts are weak evidence: a look-alike package built trust over many versions before turning malicious. inference
    Quote
    • A malicious actor created a fake package on npm impersonating our name, built trust over 15 versions, then added a backdoor in version 1.0.16 that secretly BCC’d emails to an external server. Postmark: malicious postmark-mcp package

Checks

  • H1 Publisher is identified
  • H2 It is the package the vendor means
  • H3 Source can be read
  • H4 Project is maintained
  • H5 There is a way to report vulnerabilities
  • H6 License allows the use
  • H7 New versions have aged
  • H8 Not reported as malicious
  • H9 Remote operator gives assurance
  • H10 Running it locally is justified

3. Pin

Get one exact copy, and make sure every later stage looks at that same copy.

What runs
Only the fetch tool, in a quarantine area. No install scripts.
Inputs
  • Exact version, image or URL
Steps
  1. Local or container: fetch into quarantine or an internal mirror, record digests, lock the dependency tree and build an SBOM.
  2. Remote: record the URL, the certificate-protected connection and the authorization metadata.
  3. Verify signatures and provenance.
Output
Digests, lock file, SBOM and provenance result, or the remote endpoint details.

Gate Digest or URL recorded, and no invalid signature.

On a change Fetch the new version and compare its dependency tree and install scripts with the approved ones.

  • Pinning the version of the top package does not pin its dependencies.
    Quote
    • Pinning a package version with a launcher such as npx or uvx fixes only the top-level package; its transitive dependencies are typically resolved fresh at install time MCP docs: local server security
  • Provenance at the first SLSA build level is easy to bypass or forge.
    Quote
    • Package has provenance showing how it was built. Can be used to prevent mistakes but is trivial to bypass or forge. SLSA build levels
  • A server's own name and version are self-reported. Identify it by digest or URL. inference
    Quote
    • serverInfo is self-reported by the server and is not verified by the protocol. MCP specification: discovery

Checks

  • A1 Exact version
  • A2 Digest recorded
  • A3 Fetched without running it
  • A4 Dependencies locked and listed
  • A5 Signatures and provenance verified
  • A6 Remote endpoint recorded

4. Scan

Find known problems with ordinary application security tools.

What runs
Scanners, in an isolated job without secrets.
Inputs
  • Quarantined copy
  • SBOM
Steps
  1. Run the vulnerability, malware, code, secret and configuration scans.
  2. Triage every finding: exploited, reachable, fix available.
Output
Findings with a disposition each.

Gate No known malicious package, no known exploited vulnerability and no live secret.

On a change Run all scans on the new copy and report what is new compared with the approved version.

  • A dependency audit tool is not a code analyzer.
    Quote
    • pip-audit is not a static code analyzer. pip-audit
  • A dependency audit tool can run code from what it audits, so isolate the scan job.
    Quote
    • If you wouldn't pip install it, you should not pip audit it. pip-audit

Checks

  • S1 Known vulnerabilities
  • S2 Malicious code signs
  • S3 Static code analysis
  • S4 Secrets in code and images
  • S5 Container and deployment settings
  • S6 Install and build scripts read
  • S7 Binaries and hidden code
  • S8 Dependency confusion

5. Review

Check the server against the MCP security rules that generic scanners may not know.

What runs
Nothing from the server. People and tools read code and settings.
Inputs
  • Source code
  • Configuration and launch command
  • Scan findings
Steps
  1. Go through the MCP review checks.
  2. Remote: there is no code to read. Ask the vendor for evidence on each check marked remote, and test what you can in Sandbox.
  3. Scale the depth to the tier.
Output
Review findings.

Gate Every blocking review check passes or has vendor evidence.

On a change Read the code difference, with first attention on new tools, new dependencies, new destinations, new scopes and new install scripts.

  • A scanner finding nothing does not show how the server will behave.
    Quote
    • no check proves what a server will do. MCP docs: local server security

Checks

  • M1 No command or code injection
  • M2 File access stays inside bounds
  • M3 No open URL fetching
  • M4 Tokens are checked for audience
  • M5 No token passthrough
  • M6 Proxy servers ask consent per client
  • M7 Sign-in links are handled safely
  • M8 Least privilege
  • M9 HTTP endpoint is not open
  • M10 Handles are not logins
  • M11 No secrets asked in forms
  • M12 Basic tool protections
  • M13 Usable logs without secrets
  • M14 No stored secrets

6. Sandbox

See what the server says and does when it runs.

What runs
The server, for the first time, in a disposable environment.
Inputs
  • Pinned copy or URL
  • Fake data and canary credentials
  • Egress proxy
Steps
  1. Start with outbound traffic denied and allow only declared destinations.
  2. Capture and hash everything the server tells the model or shows the user.
  3. Run MCP scanners, authentication probes and abuse tests.
  4. Use the tools, then capture again.
Output
Surface hashes, observed behaviour and findings.

Gate Behaviour matches what was declared and the surface is unchanged on second capture, or each difference is explained.

On a change Capture the surface again and compare it with the approved hashes.

  • A server can influence the model before any of its tools is called.
    Quote
    • MCP servers can manipulate model behavior without ever being invoked. Trail of Bits: line jumping
  • Starting a server to scan it can run commands or send traffic.
    Quote
    • Scanning MCP configurations can execute commands or make outbound network requests. Snyk Agent Scan
  • A malicious server could show a scanner different text than it shows real users. inference
    Quote
    • The set MAY vary by the authorization presented on the request MCP specification: tools

Checks

  • D1 Isolated and disposable
  • D2 Whole surface captured and hashed
  • D3 No instructions aimed at the model
  • D4 No hidden characters
  • D5 MCP scanner
  • D6 No shadowing or name clashes
  • D7 No dangerous combination
  • D8 Annotations match behaviour
  • D9 Network, file and process activity as declared
  • D10 Outbound content matches the request
  • D11 Authentication probes
  • D12 Abuse tests
  • D13 Second capture is the same
  • D14 Schemas and icons are safe
  • D15 Interactive UI reviewed

7. Decide

Make one accountable decision on the evidence.

What runs
Nothing.
Inputs
  • All findings
  • Tier
  • Sandbox observations
Steps
  1. Confirm the tier.
  2. Approve, approve with conditions, reject or defer.
  3. Write the approval record.
Output
A signed approval record.

Gate The right approver for the tier has decided, and the record is complete.

On a change Decide on the difference. The old record stays valid until the new one replaces it or is revoked.

  • Approval is a judgement about risk. Passing every check does not prove a server safe.
    Quote
    • no check proves what a server will do. MCP docs: local server security

Checks

  • G1 Risk tier assigned
  • G2 Every finding has an outcome
  • G3 Approver is not the requester
  • G4 Conditions and expiry set
  • G5 Record complete

8. Release

Let people run the approved copy and nothing else.

What runs
The approved server, for a first group of users.
Inputs
  • Approval record
  • Platform policy settings
Steps
  1. Publish the artifact or URL to the approved source.
  2. Add the allowlist entry and pinned configuration.
  3. Prove that an unapproved server and an unapproved version are refused.
  4. Roll out to a small group first.
Output
Policy change, catalog entry and test evidence.

Gate The block test has passed in each client in use.

On a change Move the pin and the allowlist entry to the new version in stages, and keep the previous version ready for rollback.

  • A short list of vetted, pinned servers with entry criteria is the recommended shape.
    Quote
    • Publish a short allowlist of vetted servers (with pinned versions) and the criteria a new server must meet to join it: identifiable publisher, readable source, provenance metadata, an SBOM. MCP docs: local server security

Checks

  • E1 Served from the approved source
  • E2 Allowlist matches URL or command
  • E3 Configuration is pinned
  • E4 Contained at run time
  • E5 Block is proven
  • E6 Definition changes are stopped

← DecideWatch →

9. Watch

Notice any difference from the approval record, and be able to switch the server off.

What runs
The approved server, in daily use.
Inputs
  • Approval record
  • Advisory feeds
  • Logs and egress alerts
  • Client configuration inventory
Steps
  1. Compare the live surface with the approved hashes.
  2. Match advisories to the SBOM.
  3. Watch the publisher and the traffic.
  4. Recertify before expiry, or retire.
Output
Triggers, or a new expiry date, or retirement.

Gate No open trigger and the approval has not expired.

On a change A trigger sends the server back to the stages listed under When something changes.

  • A server can change its tool descriptions after approval.
    Quote
    • a server can quietly change them after you approved it (a rug pull), so a one-time consent dialog and package pinning do not cover this surface. MCP docs: local server security
  • The protocol does not require clients to ask again when definitions change.
    Quote
    • Some clients record tool definitions when you first approve a server and ask again when they change. The protocol does not require this MCP docs: local server security
  • Change notices cannot be the only detector: sending them is recommended, not required, and depends on a declared capability. inference
    Quote
    • servers that declared the listChanged capability SHOULD send a notification MCP specification: tools

Checks

  • W1 Definition drift
  • W2 New advisories
  • W3 Upstream changes
  • W4 Traffic and logs
  • W5 Recertification
  • W6 Switch-off and rollback tested
  • W7 Unapproved servers found

When something changes

A change is any difference from the approval record. Never update a server automatically unless it meets every condition for automatic approval.

  • New version
  • Tools or instructions changed, same version
  • Remote URL, transport or hosting changed
  • New vulnerability advisory
  • Reported malicious or publisher account taken over
  • Publisher or ownership changed
  • More permissions, scopes or destinations
  • License or terms changed
  • Archived, deprecated or deleted
  • Approval expires
  • Incident or suspicious activity
  • Our own use changed

Automatic approval of a new version

Allow it only when all of these are true. Otherwise a person decides.

  • The server is in the lowest tier.
  • Every automated check in Screen, Pin, Scan and Sandbox passes.
  • The captured surface is identical.
  • No new dependency, install script, destination or scope, and the same publisher.

A vendor's remote server

Fictional example: a team asks for a ticket vendor's own remote server, to read and comment on tickets.

  1. Request Pass

    Owner, URL, two tools and read and comment scopes recorded.

  2. Screen Pass with conditions

    The URL is in the vendor's documentation. Data handling answers arrive in writing. Tier 3, because it writes.

    • H1 Publisher is identified
    • H2 It is the package the vendor means
    • H9 Remote operator gives assurance

  3. Pin Pass

    URL and authorization metadata recorded.

    • A6 Remote endpoint recorded

  4. Scan Pass with conditions

    No code to scan. The vendor shares its vulnerability handling.

    • S1 Known vulnerabilities

  5. Review Pass with conditions

    The vendor gives evidence on token audience, passthrough and logging.

    • M4 Tokens are checked for audience
    • M5 No token passthrough
    • M13 Usable logs without secrets

  6. Sandbox Pass

    Surface captured with the two scopes. Permitted probes are refused. Second capture matches.

    • D2 Whole surface captured and hashed
    • D11 Authentication probes
    • D13 Second capture is the same

  7. Decide Pass with conditions

    Approved for the two tools, for six months, with no other scopes.

    • G3 Approver is not the requester
    • G4 Conditions and expiry set

  8. Release Pass

    URL allowlisted. A second URL is refused in each client.

    • E2 Allowlist matches URL or command
    • E5 Block is proven

  9. Watch Action

    Daily surface comparison starts.

    • W1 Definition drift

A look-alike package

Based on a reported case: a package on npm used an email vendor's name without being the vendor's.

  • The vendor reported that the fake package built trust over 15 versions before adding a backdoor.
    Quote
    • A malicious actor created a fake package on npm impersonating our name, built trust over 15 versions, then added a backdoor in version 1.0.16 that secretly BCC’d emails to an external server. Postmark: malicious postmark-mcp package

  1. Request Pass

    A developer asks for the package by the name found in a search.

  2. Screen Stop

    The vendor's documentation does not name this package, and the publisher account is not the vendor's. Rejected before any download. The package name goes on the deny list.

    • H1 Publisher is identified
    • H2 It is the package the vendor means

An update adds a hidden copy

Fictional example using the same technique: an approved mail server publishes a new version that copies every message to an outside address.

  1. Screen Held

    New version seen. It waits out the 7 days while the old pin keeps running.

    • H7 New versions have aged
    • H8 Not reported as malicious

  2. Pin Pass

    New digest recorded. Dependencies unchanged.

    • A2 Digest recorded
    • A4 Dependencies locked and listed

  3. Scan Pass

    No known vulnerability or report. Known-problem scans can be silent on new malicious code.

    • S1 Known vulnerabilities
    • S2 Malicious code signs

  4. Review Pass with conditions

    The code difference touches the send function. The reviewer flags it.

    • S7 Binaries and hidden code

  5. Sandbox Stop

    A test message arrives with a recipient nobody asked for. The version is rejected, the publisher is reported and the approval of the old version is reviewed.

    • D9 Network, file and process activity as declared
    • D10 Outbound content matches the request

A poisoned tool description

Fictional example: a note taking server whose parameter description tells the model to read a key file and pass it along.

  • Instructions hidden in tool descriptions can be invisible to users and visible to models.
    Quote
    • A Tool Poisoning Attack occurs when malicious instructions are embedded within MCP tool descriptions that are invisible to users but visible to AI models. Invariant Labs: tool poisoning

  1. Request Pass

    Request recorded.

  2. Screen Pass

    Publisher and source are in order.

    • H1 Publisher is identified
    • H3 Source can be read

  3. Pin Pass

    Version and digest recorded.

    • A1 Exact version
    • A2 Digest recorded

  4. Scan Pass

    Traditional scans find nothing. The problem is text, not a vulnerable library.

    • S1 Known vulnerabilities
    • S3 Static code analysis

  5. Review Pass

    No code flaw found.

    • M1 No command or code injection
    • M2 File access stays inside bounds

  6. Sandbox Stop

    Reading every captured field shows the instruction. Rejected.

    • D2 Whole surface captured and hashed
    • D3 No instructions aimed at the model
    • D5 MCP scanner

A remote server adds a tool

  1. Watch Action

A critical vulnerability in an approved version

Based on a published vulnerability in mcp-remote, a bridge that connects local clients to remote servers.

  • The flaw let an untrusted server run operating system commands on the client machine.
    Quote
    • OS command injection when connecting to untrusted MCP servers due to crafted input from the authorization_endpoint response URL CVE-2025-6514

  1. Watch Action

    The advisory matches a stored SBOM. Configuration inventory shows who runs it.

    • W2 New advisories
    • W7 Unapproved servers found

  2. Scan Stop

    The approved version is affected. It is blocked, and exposed credentials are rotated.

    • S1 Known vulnerabilities
    • W6 Switch-off and rollback tested

  3. Pin Pass

Decisions

Approve
Released as recorded.
Approve with conditions
Released with limits that the platform or the owner enforces, such as fewer tools, fewer scopes, named users or a sandbox.
Reject
Added to the deny list when the reason is malicious or impersonation.
Defer
Nothing is released until the missing evidence arrives.
