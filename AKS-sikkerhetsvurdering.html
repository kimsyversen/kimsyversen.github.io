AKS security assessment

What you need to understand, how to go about it, and ten prioritised risks when a platform team runs Kubernetes in Azure for several application teams.

Framework OWASP Kubernetes Top 10 (2025) AKS sources Microsoft Learn, the AKS blog Facts checked 1 Nov 2026

Short version

  1. Microsoft runs the control plane in AKS. You assess what the platform team has configured around it, and the limits the application teams work within.
  2. The main question is: what can an app team, a stolen identity or a compromised pod do, and what stops them? [inference]
  3. Use the OWASP Kubernetes Top 10 as a checklist and Microsoft's AKS recommendations as guidance, adapted to your own requirements.

Kubernetes in five minutes

Kubernetes runs containers on a group of machines and keeps them in the desired state. The cluster's desired state is managed through the Kubernetes API. These are the terms you will meet, and why they matter for security.

Cluster
Control plane plus nodes.
Security: A shared cluster does not give hard isolation between teams that do not trust each other.
API server
The entry point to the Kubernetes API, used by kubectl and deployment tools, among others.
Security: Roles control API access. Admission control can also stop changes.
Node
Usually an Azure VM that runs pods in AKS.
Security: A container breakout can hit the node and other pods on it.
Pod
The smallest runnable unit: one or more containers.
Security: securityContext and the image's default user affect the privileges. Root and privileged are different things.
Namespace
A logical division, often one per team or app.
Security: A boundary for access and rules, but not hard isolation.
RBAC
Rules for who can do what: Role, ClusterRole and bindings. Can be integrated with Entra ID in AKS.
Security: Limit permissions to what the identity needs.
ServiceAccount
The identity a pod has towards the Kubernetes API.
Security: A valid Kubernetes API token gives access as that ServiceAccount. Turn off automatic mounting when API access is not needed.
Workload identity
An app in a pod can exchange a ServiceAccount token for an access token from Entra ID.
Security: Replaces stored sign-in secrets for supported services. Still limit the Azure permissions.
Admission control
Checks changes and some connections after authentication and authorisation. Reading objects bypasses it.
Security: Pod Security Admission can reject a pod even if the owning Deployment was accepted.
NetworkPolicy
Rules for pod traffic at IP and port level; needs a network solution that enforces them.
Security: Pod traffic is allowed by default; network controls can restrict it.
Secret
A Kubernetes object for passwords and keys.
Security: Base64 in the manifest is not encryption. AKS has separate storage encryption.
Ingress / Gateway
Can route traffic to apps from internal or public endpoints.
Security: Check which services are reachable from outside.

Six steps

  1. Define the scope and understand the model

    How many clusters and environments? AKS Automatic or Standard? Automatic has more pre-configured controls. Check the actual setup in both modes. Make a simple overview of what the platform team owns and what the app teams own.

    Result: scope and split of responsibility.

  2. Get read access

    Agree on Azure Reader, access to security findings and logs, and the read access you need in Kubernetes. With Entra ID, Cluster User or an equivalent permission allows fetching the kubeconfig. Without Entra integration, Cluster User gives the same access as Cluster Admin. See Microsoft's role overview.

    “Azure Kubernetes Service RBAC Reader” does not give read access to roles, bindings or Secrets. Agree on help with the RBAC check.

    Result: clear read access and documented access limits.

  3. Interview the platform team

    Use the questions below. Ask for an architecture sketch and the infrastructure code (Terraform or Bicep). It shows how things are meant to be. Compare the sketch with the risk map under the Architecture tab.

    Result: the intended design, and where to look for deviations.

  4. Check the configuration

    Go through the top 10: the Azure layer (portal or az), the Kubernetes layer (kubectl), and pipeline and registry. Take at least one app team's namespace in detail.

    Result: findings with evidence.

  5. Let the tools work

    Defender for Cloud recommendations, Azure Policy compliance, and preferably Kubescape. Tools can find misconfiguration and access risk. Add a manual review of the model and routines. [inference]

    Result: broad coverage and a check of your own findings.

  6. Assess and prioritise

    Go through the three attack paths under Top 10. Rank findings by impact and how easily they can be exploited. Give each finding an owner (platform or app team) and a concrete action.

    Result: prioritised report.

Commands with read access

Replace <rg> and <cluster>. Check the subscription in Azure CLI. kubectl uses the active context, which may point to a different cluster. The RBAC check needs read access to roles and bindings across the whole cluster.

# Version and available upgrades
az aks get-upgrades --resource-group <rg> --name <cluster>

# Configuration of the AKS resource. Look for disableLocalAccounts,
# aadProfile, apiServerAccessProfile, networkProfile, securityProfile
az aks show --resource-group <rg> --name <cluster> -o json

# Configured IP ranges for public API access
az aks show --resource-group <rg> --name <cluster> --query apiServerAccessProfile.authorizedIpRanges

# Explicit enforce label per namespace
kubectl get ns -L pod-security.kubernetes.io/enforce

# Network policies in all namespaces
kubectl get networkpolicies -A

# Services and Ingress (check internal or public exposure)
kubectl get svc -A
kubectl get ingress -A

# Kubernetes RBAC: who has access, and which rules apply?
kubectl get clusterrolebindings,rolebindings -A -o wide
kubectl get clusterroles,roles -A -o yaml

The items follow OWASP's prioritised list from 2025. The checks are adapted to AKS. Status is saved locally if the browser allows it.

Current as of 1 November 2026

  • Versions: Check the support deadline and whether LTS is enabled on the cluster. Limited “platform support” after regular support does not give security fixes for Kubernetes.
  • Ingress NGINX: The project's maintenance ended in March 2026. Microsoft supports critical security fixes for NGINX in the application routing add-on until the end of November 2026. Plan a migration.

  • Pod-managed identity: The deprecation was announced in 2022. Support for the AKS add-on ran out in September 2025. Migrate to Workload ID.

K01

Insecure workload configuration

Insecure Workload Configurations

Containers that run as root or privileged, or that get access to the node's file system (hostPath) or network (hostNetwork). Such settings can increase the damage if a container is compromised. Root alone does not mean access to the host.

Check in AKS
  • Which level is enforced? The command shows explicit namespace labels for Pod Security Admission. Baseline allows root on Linux. 
    kubectl get ns -L pod-security.kubernetes.io/enforce
  • Also check Azure Policy assignments, enforcement and exceptions.
  • What does Defender for Cloud say about privileged containers and root?

Possible findingsNo enforcement, policy that only logs, broad exceptions. A missing namespace label alone does not prove missing protection.

Compromised workloadSupply chain
K02

Overly broad permissions

Overly Permissive Authorization Configurations

Broad roles increase the damage. The right to create pods can also give access to Secrets and ServiceAccount permissions in the same namespace. See the Kubernetes RBAC guidance.

Check in AKS
  • Are Azure and Kubernetes roles limited to the necessary permissions and namespaces?
  • Who has broad permissions? Link each binding to the rules in the role it refers to. 
    kubectl get clusterrolebindings,rolebindings -A -o wide
kubectl get clusterroles,roles -A -o yaml
  • Check the Azure roles separately. Who can fetch the admin kubeconfig or use AKS Run Command? The latter can give access to a private cluster through the Azure API.
  • Does the deploy pipeline have only the permissions it needs? Microsoft advises against cluster-admin for pipelines.

Possible findingsA developer group with “temporary” cluster-admin, a pipeline with cluster-admin, a default service account with extra roles.

Stolen credentialsCompromised workload
K03

Weak secrets management

Secrets Management Failures

Secrets can leak from code, images and pods. Base64 in the manifest is not encryption. AKS has storage encryption; KMS adds an extra layer.

Check in AKS
  • Are secrets fetched from a controlled secret store, for example Key Vault through the SDK or the Secrets Store CSI Driver?
  • Is KMS encryption of secrets in etcd turned on where the requirements call for it?
  • Who can read Secrets with get, list or watch? Who can mount them in a pod?
  • Are stored keys replaced with workload identity where possible?

Possible findingsReadable secrets in Git, or long-lived sign-in keys where Workload ID could be used.

Stolen credentialsCompromised workloadSupply chain
K04

No policy enforcement in the cluster

Lack Of Cluster Level Policy Enforcement

Security policies are missing or not enforced. Audit and Warn do not reject rule violations.

Check in AKS
  • Are the necessary rules enforced, for example with Azure Policy Deny or Pod Security Admission enforce?
  • Are only images from approved registries allowed, for example your own Azure Container Registry?
  • Are deployment safeguards in Enforce mode, and which namespaces are exempt?
  • Who can grant exceptions, and are the exceptions documented and time-limited?

Possible findingsEverything in Audit mode, whole namespaces exempt.

Compromised workloadSupply chain
K05

Missing network segmentation

Missing Network Segmentation Controls

NetworkPolicy isolates pods separately for inbound and outbound traffic. Both directions are open by default. Check the actual traffic between teams and out of the cluster, including the Azure network.

Check in AKS
  • Does default-deny cover both ingress and egress for all relevant pods? Also check the allow rules in other policies. 
    kubectl get networkpolicies -A
  • Check that the network solution enforces the policies, and test actual traffic. With Cilium: also look at the Cilium policies.
  • Is outbound traffic limited to the necessary destinations? NAT alone does not filter destinations.
  • Are internal services reachable only from the intended networks and workloads?

Possible findingsNo traffic restriction between teams or to the internet.

Compromised workload
K06

Exposed Kubernetes components

Overly Exposed Kubernetes Components

A public API server without IP restriction can be reached from the internet. Stolen, valid credentials can give access.

Check in AKS
  • Is public API access turned off? VNet integration alone does not make the API server private.
  • If public access is on: is the API server limited to known IP addresses? An empty list means AKS does not filter on authorised IP ranges. 
    az aks show --resource-group <rg> --name <cluster> --query apiServerAccessProfile.authorizedIpRanges
  • Check Services and Ingress. Is the exposure internal or public, and intended? With Gateway API: also check the Gateways and their routes. 
    kubectl get svc -A
kubectl get ingress -A

Possible findingsPublic API server without IP restriction, admin tools exposed to the internet.

Stolen credentials
K07

Misconfigured and vulnerable cluster components

Misconfigured And Vulnerable Cluster Components

An outdated Kubernetes version, unpatched nodes and forgotten third-party components such as ingress controllers and operators. Outside security support you cannot count on new security fixes.

Check in AKS
  • Compare the version with Microsoft's support overview. The command shows available upgrades, not the support deadline. 
    az aks get-upgrades --resource-group <rg> --name <cluster>
  • Which cluster and node OS upgrade channel is selected, and how are timely updates ensured?
  • Which OS do the node pools run? Azure Linux 2.0 no longer gets security updates.
  • Is there a list of add-ons and third-party components, with an owner and an update routine?

Possible findingsAuto-upgrade off with no manual routine, ingress-nginx installed with Helm and forgotten.

Compromised workload
K08

From cluster to Azure

Cluster To Cloud Lateral Movement

An attacker in a pod can misuse available Azure identities. Check which resources each identity can access.

Check in AKS
  • Is Microsoft Entra Workload ID in use? Support for pod-managed identity has ended.
  • What can the kubelet identity and each workload identity access, including through inherited permissions?
  • Test pod access to IMDS (169.254.169.254). AKS IMDS restriction (preview) only covers pods without hostNetwork. The Cilium policies in Azure CNI do not cover hostNetwork pods either.
  • Are there static service principal secrets in the cluster?

Possible findingsA workload identity with Contributor on the whole subscription.

Compromised workload
K09

Weak authentication

Broken Authentication Mechanisms

Shared admin kubeconfig files, local accounts turned on, long-lived tokens or missing MFA. Static admin credentials bypass Entra ID, and so also MFA and Conditional Access.

Check in AKS
  • Is Entra ID integration on, and are local accounts off? Look for disableLocalAccounts: true in az aks show. Previously issued local certificates must be revoked during certificate rotation.
  • Does Conditional Access require MFA for those who administer the clusters?
  • Does the pipeline use workload identity federation instead of stored secrets?
  • With Entra integration: use “Cluster User” to fetch the kubeconfig, and assign API permissions separately. Avoid the admin kubeconfig.

Possible findingsLocal accounts on, admin kubeconfig shared in a team or stored in a pipeline.

Stolen credentials
K10

Insufficient logging and monitoring

Inadequate Logging And Monitoring

Without available audit logs, API calls are harder to investigate. Alerts need an owner.

Check in AKS
  • Collect the relevant audit and guard logs. kube-audit-admin leaves out get/list. For such API calls against Secrets, kube-audit can show who asked for access. Check the coverage against the AKS audit policy.
  • Do Defender or equivalent tools cover the relevant nodes and workloads? Test a documented alert.
  • Who receives the alerts, and how do they follow them up?
  • How long are the logs kept, and who can delete them?

Possible findingsDiagnostics not set up, Defender on but nobody reads the alerts.

Extra

Supply chain: images and pipeline

Supply Chain Vulnerabilities (K02 in the 2022 edition)

Images from unknown sources, vulnerable libraries, or a pipeline that many people can change. The item was K02 in the 2022 list and has no place of its own in the 2025 edition, but Microsoft's AKS recommendations have a separate section on it.

Check in AKS
  • Are images scanned in CI? Check which images Defender rescans in the registry. Inactive images may fall outside.
  • Are only images from approved registries allowed?
  • Are images signed and verified?
  • On supported Linux nodes: does Image Cleaner remove unused, vulnerable images? Windows node pools and AKS virtual nodes are not supported.

Possible findingsImages with no verified origin, or no scanning after deployment.

What is relevant, and what is not?

Microsoft runs the control plane. The customer controls their own workloads, access and data. Responsibility for nodes and network depends on the AKS mode.

Spend your time here

  • Identity and access: Entra ID, RBAC, local accounts, pipeline identity.
  • Exposure: API server, ingress and load balancers.
  • Network: between pods and out of the cluster (egress).
  • Rules for workloads: Pod Security and Azure Policy, and whether they are actually enforced.
  • Secrets and the apps' Azure identities.
  • Lifecycle: versions, upgrade channels, add-ons and third-party components.
  • Detection: logging, Defender and who responds.
  • Images and pipeline.
  • Separation between app teams: check access and network between namespaces. Consider separate clusters for teams that do not trust each other.

Less relevant for now

  • Hardening and patching the control plane (API server, etcd, scheduler): Microsoft runs it.
  • CIS checks of control plane nodes and files: not visible to the customer in AKS. [inference]
  • Physical security and hypervisor: Microsoft.
  • FIPS node pools: consider when the requirements call for validated cryptographic modules.
  • Pod Sandboxing: pods with the Kata runtime get their own kernel. For Confidential Containers (preview) Microsoft lists only Azure Linux 2.0, which is retired in AKS.
  • Service mesh and mTLS: consider if this is used as a security control. [inference]
  • Windows node pools: only if they exist.

AKS Automatic has Azure RBAC and Workload ID pre-configured. Deployment safeguards and the Pod Security baseline are enforced by default. For Workload ID, check the federation, the pod label and the app's access to the target resource.

Runtime detection in brief

Runtime detection can spot suspicious activity in running workloads. Coverage depends on sensors, logs and rules. It complements image scanning and admission control.

Six steps to introduce it

  1. Start with the threat scenarios

    Pick scenarios such as a shell in a container, privileged pods, Secret reads and access to IMDS. Find out which events and alerts the tool actually supports.

    Result: 5-10 scenarios with observable signals.

  2. Map a baseline per workload

    Map normal processes, outbound destinations and file paths. Use this to judge alerts. Start with the most exposed apps.

    Result: normal behaviour per workload.

  3. Choose data sources

    Combine relevant node sensors and Kubernetes audit logs. Check which scenarios the tool supports, and test the coverage.

    Result: coverage map: which scenario is caught by which source.

  4. Run in monitor mode first

    Start with alerting and tune the rules. Consider blocking only if the tool supports it and the consequences are tested.

    Result: rule set tuned to your own workloads.

  5. Simulate attacks in a test environment

    Use the tool's documented simulations, for example Defender's test simulations. Measure the expected alert and the delay. A shell or a file change does not necessarily trigger an alert.

    Result: test result per scenario, with time to alert.

  6. Define the operating model before rollout

    Who triages the alerts, in which SIEM, how long logs are kept, and what the response is: isolate the pod, take an image of the node, notify the app team. Measure false positives per week and time from event to alert.

    Result: owner, response routine and key figures.

What can be detected?

These are test scenarios, not a guarantee of coverage in Defender. Check the tool's support per OS and installation, and test the expected alerts.

Signals to test

  • Calls to pods/exec in the audit log, or a shell process observed in the container.
  • A binary that was not in the image and gets run.
  • Changes to critical files, new setuid binaries.
  • New rolebindings or get on secrets in the API.
  • Contact with known malicious destinations, if threat intel is up to date.
  • Privileged pods, hostPath and hostNetwork, which can also be checked statically.

False positives or need context

  • A shell during legitimate troubleshooting (kubectl debug, operations work).
  • Startup scripts, cron jobs, health checks and package managers in normal operation.
  • Calls to IMDS from apps that use managed identity. [inference]
  • Sidecars, init containers and DaemonSets that look like unexpected processes or network activity on the node.
  • Load tests and service discovery that resemble a port scan.
  • High CPU or crypto use in legitimate apps.

An alert must be assessed against the event and its context before you draw conclusions.

Check the static part first

The command checks existing pod specifications. It needs jq and permission to list pods in all namespaces. It has not been run against a cluster here. [unverified]

# Pods with hostNetwork, hostPID, a privileged container or hostPath
kubectl get pods -A -o json | jq -r '.items[] | select(.spec.hostNetwork==true or .spec.hostPID==true or any((.spec.containers[]?, .spec.initContainers[]?, .spec.ephemeralContainers[]?); .securityContext.privileged==true) or any(.spec.volumes[]?; .hostPath!=null)) | "\(.metadata.namespace)/\(.metadata.name)"'
