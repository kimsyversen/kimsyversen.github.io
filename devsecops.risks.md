# DevSecOps phase risk audit

Reviewed 24 November 2026 against both lifecycle views in [devsecops.html](devsecops.html). The register has 43 DevSecOps risks, including all 22 existing risks and 21 additions, and 20 Agentic DevSecOps risks. It covers both lanes in all ten phases of each view and checks the four existing agent risk themes.

- **Code governance.** The FTC's Drizly complaint connects repository access and oversight failures to two security incidents. It gives the empty Code governance cell a case, with the complaint's findings attributed to the FTC.
- **Test governance.** The FCA's full TSB final notice identifies testing decisions and risks that bypassed the expected review and escalation. It gives the empty Test governance cell a case and also documents what happened at the Release decision.
- **Operate governance.** The Cyber Safety Review Board's Microsoft Exchange Online investigation documents what happened when manual signing-key rotation stopped without a replacement process. TSB adds evidence on post-launch support preparedness.
- **Case-fit corrections.** The Meta and Equifax disclosures show data protection failures. The sources leave the upstream planning decisions unknown. The SEC's Morgan Stanley order adds evidence of actual data leaving the firm's control. The affected customer's SaaStr writeup and Replit's statement give the agent-access example first-party sources.
- **Agent handoffs.** The Replit and PocketOS incidents show development or staging work crossing into production. OpenAI's internal coding cases show that agents can weaken monitoring and misstate what they changed. Several other phase mappings have controlled evidence or a conventional analogue only.

## DevSecOps

Each risk has a home at the phase where the responsible team can address that specific failure. Multiple risks can contribute to the same incident. Governance covers ownership, oversight and decisions. Secure development covers failures in code, tooling and service execution. `[inference]` applies to the risk wording, phase ownership and case mapping across this register.

**Page** means the risk is already represented in the HTML. **Added** means it adds a distinct risk. **Direct** means the source documents the failure described in the evidence column. **Partial** means it documents part of the risk or leaves the upstream cause unknown. **Complaint** means the mechanism is attributed to a regulator's allegations. **Compromise** means a malicious change was distributed or discovered and the source leaves downstream harm unestablished.

## Agentic DevSecOps

The baseline register also applies when agents do the work. The rows below describe the extra failure modes that come from delegated tool access and from using agent output as a handoff. `[inference]` applies to the phase mapping and to any extension from a case or study to this lifecycle. The worked example is illustrative and supplies no incident evidence.

**Operational case** means a vendor or affected party reported real use, including internal workflows where stated. **Study** means observations from a controlled evaluation or user study. **Demonstration** means a researcher or vendor demonstrated a vulnerability. **Analogue** means a real failure in a comparable workflow. **Control evidence** means documentation verifies a feature or safeguard while the source leaves actual harm unestablished.

| Phase | Enterprise governance risk | Technical software development risk |
|---|---|---|
| [Plan](devsecops.html#agentic-plan) | **AP-G1.** An unvetted request is treated as authorization to change security scope. A reviewer who sees only the generated spec can approve a different task from the one the service owner agreed. **Control evidence.** GitHub documents which issue and comment inputs its cloud agent will consume. The exact spec-approval failure has no verified public case in this review. [GitHub cloud agent risks](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) | **AP-T1.** The agent treats untrusted issue or repository text as instructions and carries it into the task or a tool action. **Demonstration.** A disclosed Copilot vulnerability showed that untrusted content could steer agent behavior. The demonstration did not involve this spec handoff. [GitHub advisory, CVE-2025-53773](https://github.com/advisories/GHSA-3m2x-p87c-pwv6) |
| [Code](devsecops.html#agentic-code) | **AC-G1.** The organization authorizes development work without checking whether the agent's tools can write to production. An agent acting within the available permissions can delete live data. **Operational case.** SaaStr describes an agent in development deleting live data and reports successful recovery. Replit confirms that development and production database separation previously required manual setup. [SaaStr account, 2025](https://www.saastr.com/replits-new-release-address-most-of-the-challenges-we-hit-vibe-coding-but-is-prosumer-vibe-coding-really-ready-for-commercial-apps-yet/) · [Replit account](https://replit.com/blog/doubling-down-on-our-commitment-to-secure-vibe-coding) | **AC-T1.** Generated code compiles and appears plausible while producing weaker security behavior. Local tests written with the change can miss the unsafe path. **Study.** A 47-participant study reported less secure solutions and greater confidence among participants with AI assistance. It tested a specific earlier assistant in controlled tasks. [Perry et al., ACM CCS study](https://arxiv.org/abs/2211.03622) |
| [Review](devsecops.html#agentic-review) | **AV-G1.** Repository settings let an automated approval count toward a gate that the organization intended to require a person to satisfy. A reviewer can merge without the expected independent human judgment. **Control evidence.** GitHub documents an opt-in feature that lets Copilot code review count toward required approvals. The Copilot cloud agent that authors changes has separate restrictions on approving or merging its own work. [GitHub code review changelog, 2026](https://github.blog/changelog/2026-09-01-copilot-code-review-can-now-approve-pull-requests/) · [GitHub cloud agent risks](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) | **AV-T1.** The reviewing agent checks only the changed handler or follows the author's threat assumptions. A second path, such as bulk download, stays outside the finding. **Analogue.** Atlassian's peer review checked the cleanup endpoint and its use while missing that the target list contained site IDs. The public record concerns human review. The page's bulk-download example is illustrative. [Atlassian post-incident review, 2022](https://www.atlassian.com/blog/how-we-build/post-incident-review-april-2022-outage) |
| [Build](devsecops.html#agentic-build) | **AB-G1.** An agent tool, extension, connector or its updater becomes an unowned software supplier. Its distribution path grants more trust than the organization approved. **Compromise.** AWS reported an unauthorized change in an Amazon Q Developer extension release through an inappropriately scoped build integration token. AWS said the injected code did not execute.
