# Enterprise MCP security requirements

Reviewed 2026-11-19 against the [current MCP specification (2026-07-28)](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) and applicable [NIST SP 800-53 Rev. 5 controls](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final).

**Verdict. Keep all 13 principles and adopt the revised wording below.** Three independent reviewers checked the original and revised requirements from protocol and identity, governance and privacy, and application security and operations perspectives. No material findings remained in the revised high-level security baseline after re-review. The review covered the requirements on paper. Deployment validation remains separate.

| ID | Finding in the original | Verified enterprise requirement |
|---|---|---|
| **MCP-01 · Governance** | Server and tool inventory misses hosts, intermediaries, and other capabilities. | Enterprise MCP integrations must be approved before use, inventoried, and assigned an accountable owner. The inventory must cover local and remote hosts and clients, servers, intermediaries, and enabled capabilities, including tools, resources, prompts, and extensions. Record approved uses and data and trust boundaries. [MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture) · [NIST CM-8, SA-9](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-02 · Traceability** | Identity and delegation can get lost across service calls or deferred work. | Every enterprise operation performed by an MCP-enabled agent must be attributable across components and downstream systems to an authenticated initiating user or a uniquely identified, authorized workload with an accountable owner. Preserve the executing identity and applicable delegation. [NIST IA-2, IA-9, AU-3, AU-16](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-03 · Authentication** | Token trust and downstream credentials are implicit. | Verify caller and service identities and protect channels and credentials according to the transport and trust boundary. Where tokens are used, validate the trusted issuer, intended audience, and validity. Prohibit token passthrough and use credentials intended for the downstream service. [MCP authorization and token handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#token-handling) · [MCP security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough) |
| **MCP-04 · Authorization** | Enforcement needs a default decision and a per-request scope. | Deny by default. Enforce least privilege independently of the AI model on each protected request, checking the capability, action, target resource, tenant where applicable, and the caller’s effective authority. [MCP tools security](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations) · [NIST AC-3, AC-6](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-05 · Human oversight** | User consent, approval of a specific action, and unattended workload authorization need distinct rules. | The host must obtain explicit, informed, scoped, revocable user consent before operations in a user context, including data access, tool use, and onward sharing. Honor that scope for deferred work. An authorized human must approve each high-risk action and its material parameters before execution unless an approved policy expressly preauthorizes that action class within documented, time-bounded, revocable limits. Define which actions always require individual approval. Unattended workloads require their own scoped, time-bounded, revocable authorization and must honor applicable consent and approval requirements. [MCP security and consent principles](https://modelcontextprotocol.io/specification/2026-07-28#key-principles) · [MCP tools interaction model](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#user-interaction-model) |
| **MCP-06 · Data protection** | Downstream sharing, secondary use, retention, and deletion are implicit. | Apply enterprise classification, privacy, and information protection requirements throughout the data lifecycle. Minimize data and restrict use and disclosure to authorized purposes and recipients, including model providers and other third parties. Apply retention and deletion rules to stored data, caches, logs, and traces. [MCP data privacy principles](https://modelcontextprotocol.io/specification/2026-07-28#key-principles) · [NIST AC-4, PT-2, PT-3, SI-12](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-07 · Input and output security** | The host and server need explicit responsibilities, including for chained calls. | Treat external content and model-generated requests as untrusted, including prompts, resources, tool metadata, and results. Servers must validate inputs and sanitize outputs. Clients must validate results before use. Enforce authorization independently on every resulting action or disclosure. [MCP tools security](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations) · [NIST Generative AI Profile, §2.9](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf) |
| **MCP-08 · Integrity and supply chain** | Source trust alone leaves software provenance, configuration changes, and changing tool definitions implicit. | Use approved sources and verify the provenance and integrity of software, dependencies, configuration, and updates. Control installation and changes, including changes to tool definitions, and reapprove material capability changes before use. [MCP tool-list changes](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#list-changed-notification) · [NIST supply-chain guidance](https://csrc.nist.gov/pubs/sp/800/161/r1/upd1/final) |
| **MCP-09 · Isolation** | The original misses host-side isolation between servers and separation of credentials, context, and caches. | Enforce risk-appropriate isolation across user, service, tenant, and trust boundaries. Cover host and server execution, credentials, context, state, caches, filesystem access, and network access. Restrict outbound connections to approved destinations or destination classes. [MCP architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture#design-principles) · [MCP local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#local-mcp-server-compromise) |
| **MCP-10 · Security enforcement** | The scope needs to follow paths available to the integration. | Enforce applicable enterprise controls on every path the integration or its agents can use to reach protected operations, including direct APIs, alternate endpoints, intermediaries, and downstream service calls. Deny paths where required controls cannot be enforced. [MCP security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough) · [NIST AC-3, SC-7](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-11 · Monitoring and auditing** | Audit integrity, retention, and response are implicit. | Capture and correlate security-relevant events across components, including denied requests, approvals, and outcomes. Protect records against unauthorized access and tampering, retain them under policy, minimize sensitive content, and monitor for events that require a response. [MCP tools security](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations) · [NIST AU-2, AU-3, AU-6, AU-9, AU-11](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) |
| **MCP-12 · Operational security** | Revoking access leaves queued and in-flight work, retries, and uncertain outcomes to handle. | Enforce resource and workflow limits. Deny protected operations when required controls cannot be verified. Handle retries, interrupted operations, and uncertain outcomes safely. Revoke access within defined deadlines, stop queued work, and maintain tested procedures to contain in-flight work and recover safely. [MCP task cancellation](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks#task-cancellation) · [NIST incident response guidance](https://csrc.nist.gov/pubs/sp/800/61/r3/final) |
| **MCP-13 · Security lifecycle** | Assessment triggers and secure retirement need explicit coverage. | Assess and test integrations before production and after material changes. Reassess periodically, manage and remediate vulnerabilities, keep components on supported versions, and retire integrations securely. [NIST CA-2, CA-7, RA-5, SI-2, SA-22](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) · [NIST Secure Software Development Framework](https://csrc.nist.gov/pubs/sp/800/218/final) |

The bounded exception in **MCP-05** preserves the original policy choice. The enterprise must decide which high-risk actions always require individual approval. That decision is distinct from the host’s responsibility to obtain user consent, and each deployment must turn it into enforceable rules. [MCP consent principles](https://modelcontextprotocol.io/specification/2026-07-28#key-principles)
