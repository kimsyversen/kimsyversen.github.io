Copilot control boundaries

  • VS Code device policies govern editor features such as extension allowlisting. Check whether an AI policy also reaches the selected harness.
  • GitHub Copilot enterprise-managed settings apply to supported Copilot clients and Agent Host capabilities, including managed permissions and terminal sandbox settings [preview]. When a managed setting and a device policy set the same control, the managed setting wins. Test delivery and enforcement in the session.
  • Harness choice To block the Local, Claude and Codex harnesses, set vscode.temporaryAllowLocalHarness to false in managed settings (VS Code 1.143 or later). Managed settings disable Claude and Codex by default. If permitted, they run without Copilot’s managed permission, sandbox, MCP and plugin controls. Local is deprecated, will be removed in February 2027 and does not enforce runtime-only sandbox and permission rules.
  • GitHub organisation and enterprise settings govern service and account features such as model availability. Check the effective account alongside device and runtime policy. VS Code enterprise AI settings

D01

Malicious packages and install scripts

OWASP ASI04 Agentic Supply Chain Vulnerabilities

A dependency install run through Copilot’s terminal tool can execute package or project code. Microsoft documented credential theft and package republishing through npm install scripts in ChainDrop.

Check
  • Can Copilot install dependencies from public registries? Use an approved registry or proxy where policy requires package blocks or a release cooldown. A managed .npmrc sets defaults that a project, environment variable or command line can override.
  • For npm 12, review allowScripts in package.json, or allow-scripts in .npmrc where package.json has no entries, and check that dangerously-allow-all-scripts is disabled. Review the project’s npm extension separately: root .npm-extension.mjs or .npm-extension.cjs, or the file selected by extension-file. npm runs it during npm install and checks its recorded hash during npm ci.
  • Include each package manager the VS Code fleet uses. Decide who can approve urgent updates that a cooldown would block. Test using an approved package and a blocked package in the Copilot terminal.

Look forDirect public registry access, broad script grants, repository-controlled install settings and unreviewed npm extensions.

D02

Code runs when a project is opened

OWASP ASI05 Unexpected Code Execution

A repository can carry VS Code tasks and workspace settings into a clone. In a trusted folder, a folderOpen task can run when automatic tasks are allowed. A Dev Container can also declare an initializeCommand that runs on the host.

Workspace Trust disables agents in untrusted folders and limits tasks and other execution features. An archive or shared folder can also carry local .git metadata. Treat that metadata as a separate input before opening the folder in VS Code.

Check
  • Open unfamiliar folders in Restricted Mode. Check inherited trust from parent folders, especially broad development or download directories. Review workspace files before granting trust.
  • Keep automatic tasks off for unreviewed projects. Review .vscode/tasks.json, executable paths in settings, .code-workspace files, Dev Container setup, .vscode/mcp.json, .mcp.json and agent hooks when present. Workspace MCP servers can start without a separate trust prompt once the project is trusted.
  • Setting ChatHooks to false stops repository and custom agent hooks in Copilot sessions, not user, policy or installed plugin hooks. ChatAllowManagedHooksOnly limits hooks to enterprise-managed sources and plugins that policy force-enables.
  • Prefer a fresh clone from an approved source when files arrive with local Git metadata. Require code-owner approval for execution-sensitive files on shared repositories, then verify the branch rule and who can bypass it.

Look forBroad trusted roots, automatic tasks enabled, downloaded Git metadata and unreviewed workspace configuration.

D03

Malicious or hijacked extensions

OWASP ASI04 Agentic Supply Chain Vulnerabilities

VS Code extensions can execute code in the extension host with the developer’s permissions. AWS confirmed that a 2025 release of the Amazon Q Developer extension for VS Code (1.84.0) shipped malicious code. AWS says the code failed to run because of a syntax error.

Check
  • Deploy AllowedExtensions with approved extension IDs, including the required GitHub Copilot extensions. Inventory installed versions and publishers across the profiles and remote extension hosts in use.
  • Check approvals for local VSIX packages. Microsoft says the allowlist checks declared identifiers. Verify origin and integrity separately when distributing local packages.
  • For managed updates, use a staged rollout or ExtensionsAutoUpdateDelay with a route for urgent fixes. The delay applies only when extensions.autoUpdate is on (policy ExtensionsAutoUpdate). Review extensions that also expose tools to Copilot.

Look forMarketplace or local packages outside the approved inventory, broad publisher grants and untracked remote extension hosts.

D04

Secrets and long-lived tokens on the machine

OWASP ASI03 Identity and Privilege Abuse · MCP01 Token Mismanagement and Secret Exposure

GitHub Copilot can reach secrets through file context, terminal commands, credential helpers or tools with their own tokens. The Copilot sandbox enables Git and GitHub CLI credential integration by default. Dev Containers can also reuse Git credentials and forward SSH agent access.

Check
  • Keep production credentials and secret files out of the development environment where practical. Scope and expire GitHub, registry and cloud credentials. Inspect which identities an agent session can actually use, including in a Dev Container.
  • In Copilot Agent Host, check managed permissions.deny rules for sensitive reads and sandbox.userPolicy.filesystem.deniedPaths [preview] for sandboxed processes. Without managed sandbox settings, add deniedPaths in chat.agent.sandbox.fileSystem.userConfiguredPaths. Check /sandbox policy and test file-tool access and terminal access separately with dummy secrets.
  • By default the sandbox can read developer tool folders and caches, including registry tokens, and write to shared build caches. Turn off chat.agent.sandbox.fileSystem.allowDevToolAccess where builds allow it and grant narrower paths. Set chat.agent.sandbox.credentials.authenticategit and chat.agent.sandbox.credentials.authenticategh to false where sandboxed commands should not use those credentials. To enforce both, set managed sandbox.allowDevToolAccess, sandbox.auth.git and sandbox.auth.gh to false [preview] and require the sandbox as in D07.
  • Check where Git stores credentials. The store helper uses plaintext. Inspect SSH forwarding, environment variables and credential helpers before approving agent commands.
  • Use GitHub content exclusion for supported Copilot workflows. GitHub documents limits for indirect access, symlinks, remote filesystems and third-party MCP tools. Check these paths separately.

Look forProduction tokens in local files, broad forwarded credentials, and a secret path excluded from one tool but readable through another.

D05

Prompt injection and poisoned instruction files

OWASP ASI01 Agent Goal Hijack

An issue, web page, repository file or MCP result can carry instructions that redirect Copilot. The Copilot harness also loads project guidance from .github/copilot-instructions.md, AGENTS.md and scoped instructions. Treat changes to that guidance as changes to agent behaviour.

Check
  • Verify which instructions load for the selected Copilot session and repository root. Review project and user-level instructions before giving the agent access to unfamiliar workspaces or external content.
  • Require review for changes to instructions, custom agents and skills. Use Workspace Trust for unfamiliar projects and a separate approval or permission control for sensitive actions.
  • Use harmless sample content to check how the session handles a misleading instruction and whether the target tool still requires approval. Include tool results and pages in the test if the team uses them.

Look forInstruction changes with no owner, unexpected instruction sources and sensitive tool actions available without review.

D06

Untrusted MCP servers, plugins and skills

OWASP ASI04 · MCP03 Tool Poisoning · MCP07 Insufficient Authentication and Authorization

Copilot can send context to a remote MCP service and read its results. A locally launched server can execute code on the workstation. Plugins and skills can add tools or instructions, so review both the source and the capabilities enabled by a package.

Check
  • Inventory editor-managed servers and Agent Host-owned servers separately. Use ChatMCP and ChatAllowedMcpServers for editor-managed servers. Check the GitHub-managed allowedMcpServers and deniedMcpServers for Agent Host. Allow remote servers by serverUrl and local servers by exact serverCommand. Users choose server names, so a serverName rule does not prove identity. GitHub exempts built-in first-party servers from deny rules. Review their tools separately.
  • For each server, approve the executable or endpoint and confirm its tools, data recipients and downstream access. Verify that remote services validate the token audience and use separately scoped credentials for downstream calls.
  • If plugins are unnecessary, disable plugin integration. Otherwise review enabled plugins, their marketplaces, bundled servers and any automatic updates. In the deployed Copilot harness, check whether the intended settings restrict installation, execution or both.
  • To block standalone skills, custom agents, hooks, MCP servers and executable Copilot extensions in Agent Host sessions, set GitHub-managed strictPluginOnlyCustomization to true and test it in a session. Eligible plugins and managed settings can still supply them, so restrict plugin sources with strictKnownMarketplaces.

Look forA registry treated as the only enforcement layer, unreviewed local executables and remote tools with broad write scopes.

D07

No sandbox and open network

OWASP ASI05 · makes exfiltration in ASI01 and ASI03 possible

Copilot’s default tools can sandbox terminal commands and locally launched MCP servers. The sandbox setting chat.agent.sandbox.enabled defaults to off. With the sandbox on, outbound network access is still allowed by default. Test the effective boundaries on the host that runs the tools.

Check
  • Check the deployed OS and tool implementation. Use GitHub’s managed sandbox settings [preview]: set sandbox.enabled, failIfUnavailable and sandboxMcpServers to true and allowBypass to false. Hosts that cannot enforce the sandbox then block model and tool execution. Adding sandbox settings blocks older clients, including VS Code before 1.141.0. Without them, set chat.agent.sandbox.enabled to on and chat.agent.sandbox.allowUnsandboxedCommands to false. Users can change both, so check each session with /sandbox policy. Windows support is experimental [preview]. Assess the VS Code Local harness terminal sandbox separately if it is still enabled.
  • Test limits on workspace writes, reads outside the workspace, outbound network, access to local services and requests to run outside the sandbox. Use dummy files and approved test destinations.
  • To block outbound access in sandboxed sessions, set chat.agent.sandbox.network.allowNetwork to false. Managed enforcement sets sandbox.userPolicy.network.allowOutbound to false [preview].
  • Test egress separately for the built-in shell, browser or fetch tool, extensions, and local or remote MCP. In Copilot sessions, ChatAgentNetworkFilter covers the integrated browser and, with domains set in ChatAgentAllowedNetworkDomains, blocks web fetch outside that list. Terminal coverage depends on harness, platform and sandbox settings. Verify account or tenant restrictions where an allowed host also accepts personal accounts.
  • For higher-risk sessions, use a separate execution environment with minimal mounts, credentials and network access. Check whether a Dev Container forwards credentials or exposes host services before relying on that boundary. With the sandbox on, new Dev Container sessions get Docker options that relax the container’s isolation from the host. Other processes in the container do not automatically get the sandbox’s protection, so do not rely on the container alone to protect the host.

Look forA sandbox toggle treated as fleet enforcement, untested fallback prompts and an allowed service that also accepts personal accounts.

D08

Approval bypass

OWASP ASI02 Tool Misuse · ASI09 Human-Agent Trust Exploitation

Copilot tool approval depends on the selected permission level, tool, prior grants and harness. A researcher showed that a prompt injection could make Copilot in VS Code add chat.tools.autoApprove to project settings and turn off confirmations (CVE-2025-53773, fixed in August 2025). The CVE record lists Visual Studio 2022 17.14 versions before 17.14.12 as affected. Keep the deployed versions patched and validate the effective approval rules.

Check
  • Set ChatToolsAutoApprove to false to disable global auto-approval. Use GitHub-managed session permission settings to restrict bypass and Assisted permissions separately. Verify that the intended session modes and grants can be used only where policy permits.
  • Use GitHub managed permissions.ask for Copilot Agent Host actions that require fresh approval. Use permissions.deny for prohibited actions. Managed rules select shell commands, file reads, file edits and domains. No MCP tool selector is listed, so limit MCP servers as in D06. Confirm each rule in a session.
  • Where terminal commands must ask, set managed permissions.ask Shell rules. Do not rely on ChatToolsTerminalEnableAutoApprove alone: VS Code docs differ on whether sandboxed and read-only commands still run without a prompt. Set ChatAgentHostCustomTerminalTool to false to keep sessions on the built-in shell.
  • With ChatToolsAutoApprove false, confirmations offer only one-time approval and saved approvals are not applied. Check the destination and scope shown in each prompt before granting file, network or tool access.

Look forAutonomous permission levels in routine sessions, durable grants for state-changing tools and prompts that obscure the destination.

D09

No inventory, version floor or agent telemetry

OWASP MCP08 Lack of Audit and Telemetry · ASI10 Rogue Agents (secondary, detection side)

To determine exposure, record the VS Code build, GitHub Copilot version, harness, extension and MCP inventory, and effective policy. Defender process events can record command lines for the created and initiating processes. Correlate them with Copilot telemetry when investigating tool activity.

Check
  • Inventory the deployed builds and extensions from endpoint management. Check updates after a security fix and confirm which harness and shell implementation users actually run.
  • Set a version floor and enforce it through endpoint management. VS Code says the managed-settings service can also require a minimum version.
  • Run Developer: Policy Diagnostics on a managed device, then exercise the intended restriction in a real session on each supported OS and harness. Handle the report as sensitive because it can include account and session details.
  • For monitoring, send Copilot OpenTelemetry data to an approved collector. Correlate a harmless test action with endpoint events where it creates a process. Check coverage for MCP and for other tool actions that may lack a matching process event. Identity capture is off by default. If you need attribution, enable it and test it in Agent Host, because the VS Code and GitHub documents disagree on support. See D17 for content capture.

Look forConfigured policy with no enforcement test, missing harness inventory and endpoint events treated as a complete session history.

D10

Code and context sent to unapproved AI services

Data governance

Copilot requests can include code, prompts and relevant tool results. Model settings, the signed-in GitHub account and bring-your-own-key providers determine which services can receive the data. Remote MCP is a separate recipient covered in D06.

Check
  • Use ChatApprovedAccountOrganizations with explicit organisation names. It checks membership. Verify company-managed identity separately if required, and check the effect of switching accounts.
  • Use GitHub organisation or enterprise policy for approved Copilot models and features, and check availability of models configured with personal provider keys. VS Code says those credentials are subject to the other provider’s terms.
  • Check which source code and tool outputs may go to Copilot under company data rules. Verify provider retention, training use, residency and deletion terms for the features in use.

Look forPersonal Copilot accounts with company access, unapproved model credentials and unknown handling terms for code or tool results.

Governance

Incident response

  1. Contain the workstation and affected remote hosts. End active Copilot sessions and remote connections through your response process. Assess the GitHub identity’s access from other devices.
  2. Preserve evidence before cleanup. Collect available Copilot logs and session data, VS Code and Agent Host configuration, extensions, tool definitions, and GitHub and endpoint events. Limit access to the collected data.
  3. Revoke exposed access. Check GitHub sessions and tokens, SSH, registry and cloud credentials, and MCP authorisations. Rotate credentials from a clean environment.
  4. Check for persistence. Review VS Code user and workspace settings, tasks, extensions, Copilot instructions, custom agents, skills, hooks, plugins and memory (D14), saved approvals and path grants on each Agent Host, MCP configuration, Git hooks, operating system scheduled tasks and remote tunnel services.
  5. Trace downstream changes. Check pushes, pull requests, workflow runs, package releases and actions taken by connected tools. Restore the workstation and affected projects from a known-good state.
