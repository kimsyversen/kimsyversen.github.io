Developer workstation risk map

Where the ten most important risks sit when developers run VS Code, the git CLI and AI coding agents on their own machine, what to check for each, and seven further risks to keep in view.

Frameworks OWASP Agentic Top 10 (2026), MCP Top 10 (beta) Vendor sources VS Code, Claude Code, OpenAI Codex, GitHub, Microsoft Defender, npm, Git Facts checked 29 Oct 2026; corrections 30 Oct and 1 Nov 2026 Review persona-based passes and two audit rounds, records not attached

In short

  1. Everything on the laptop starts with the developer's rights: VS Code, extensions, agents, MCP servers and install scripts. A sandbox or per-tool permission narrows that only where it is on and covers the tool. Everything else can read what the developer can.
  2. The main question is: what can untrusted content, a bad add-on or a stolen token make the machine do, and what stops it? [inference]
  3. Several documented 2025 and 2026 incidents entered through things developers fetch: repos, extensions, packages and agent add-ons. The incidents cited here are a sample, not a defined dataset, so no share is claimed.

Current as of 1 November 2026

  • npm: npm 12 has been out since July 2026 (12.2.1 is current on the npm registry). It no longer runs dependency install scripts unless they are approved. It still runs the project's own .npm-extension.mjs or .npm-extension.cjs on npm install (not on npm ci), and dangerously-allow-all-scripts switches script approval off.
  • GitSpawn: at publication on 1 September 2026, four of eight findings across seven agents were unpatched, including a second Claude Code path still open on 2.1.252. It needs a repo that arrives as files with its .git folder; a normal clone does not carry it. A global core.fsmonitor of false does not help, because the repo's own config wins.
  • Plugin4Shell: fixed in Claude Code 2.1.179 and Codex 0.146.0. At disclosure on 18 September Copilot had no client fix and Gemini CLI was not being fixed.
  • GitHub package firewall: public preview since 20 October 2026 for GitHub Enterprise Cloud, npm only.
  • Sandboxes on Windows: Claude Code does not sandbox on native Windows (WSL2 only). VS Code's Windows sandbox is experimental and needs a recent Windows 11 build.

D01

Malicious packages and install scripts

OWASP ASI04 Agentic Supply Chain Vulnerabilities

A package install can run code before anyone reads it. ChainDrop (Microsoft, 4 August 2026) used a preinstall script in more than 400 npm packages to steal credentials and republish packages. Some copies had valid provenance from a real CI workflow, so provenance alone does not prove safety.

In August 2025 the s1ngularity malware ran installed AI CLIs with their permission checks off to search the disk for secrets.

Check
  • Is npm 12 (released July 2026) or later in use? It runs dependency install scripts only when approved. It needs Node.js 22.22.2, 24.15.0 or 26 and later, so plan it as a fleet change. 
    npm --version
npm config get ignore-scripts min-release-age dangerously-allow-all-scripts ignore-extension extension-file
  • Do any projects bypass or widen script approval? dangerously-allow-all-scripts runs every dependency install script; npm calls it a migration escape hatch only. Review allowScripts grants in package.json and .npmrc, since a repo can carry its own [inference]. [not run here]
  • Is project code that runs outside script approval reviewed? npm install runs a root .npm-extension.mjs or .npm-extension.cjs before dependencies resolve; npm ci only checks its recorded hash. ignore-extension or ignore-scripts skips it. The docs do not say whether script approval covers it, so treat it as uncovered [inference]. Put these files under code-owner review (D02).
  • Is there a cooldown before new versions install? min-release-age in a managed npmrc is only a default: a command-line flag, an environment variable or a project .npmrc overrides it. To enforce it, use the registry or a package firewall (GitHub's is in public preview, npm only).
  • Is there a route for urgent security fixes? If a cooldown blocks the fix npm audit fix would install, npm keeps the vulnerable version and warns. min-release-age-exclude exempts named packages. Agree who grants exceptions and for how long. [inference] for the process.
  • Do installs go through an internal registry or proxy rather than straight to public registries?
  • Are pnpm, Yarn, pip and other package managers covered too? [inference]

Typical findingsnpm 10 or 11 with scripts on, no cooldown or one that a flag or project file can undo, provenance treated as proof of safety, script approval switched off or widened, root extension files nobody reviews.

D02

Code runs when a project is opened

OWASP ASI05 Unexpected Code Execution

Project files that survive a clone can name a program to run: .vscode/tasks.json, workspace settings, .devcontainer/devcontainer.json (its initializeCommand runs on the host), .claude/settings.json, .mcp.json and npm's root .npm-extension files. North Korea's Contagious Interview campaign sends fake coding tests whose tasks.json runs on folder open.

.git/config and hooks arrive only when a project is shared as files, such as a zip. In GitSpawn (September 2026), background Git calls in seven agents ran a command from that config, sometimes before the trust prompt.

Check
  • Is Workspace Trust left on, and do developers choose restricted mode for unreviewed code? CLI agents have their own trust prompts, and GitSpawn showed that some run code before them.
  • Are automatic tasks kept off? task.allowAutomaticTasks is off by default, but VS Code asks once per workspace whether to allow them, and on runs them in every trusted workspace without asking. Automatic tasks never run in an untrusted workspace. Decide whether developers may answer Allow, and check that no settings file sets on.
  • Are agents on current versions? See the Current box above.
  • Did the repo arrive as files rather than as a clone? Then read its Git config before an agent opens the folder, and look in .git/hooks too. Look for fsmonitor, hookspath, sshcommand, pager, editor, filter, textconv and include. 
    git config --file <repo>/.git/config --list --show-origin
  • Do not rely on git config --global core.fsmonitor false. A repo's own config overrides it; this was tested here. An environment override (GIT_CONFIG_COUNT) does block it, but it also breaks legitimate fsmonitor use, and it does not cover the other command-bearing settings.
  • Do changes to .vscode/, .claude/, .devcontainer/, AGENTS.md, .npm-extension.* and .npmrc need code-owner approval? A CODEOWNERS file on its own only requests review. Turn on Require review from Code Owners in branch protection or a ruleset, give CODEOWNERS itself an owner, and review who can bypass the rule. [inference] for the bypass point.
  • Is Git patched for CVE-2025-48384 on macOS and Linux? Windows is not affected. Distributions backport fixes without changing the version string, so use vulnerability-management inventory rather than git --version.

Typical findingsTrust granted to every folder, repos from shared drives opened straight in an agent, no review on config folders.

D03

Malicious or hijacked extensions

OWASP ASI04 Agentic Supply Chain Vulnerabilities

An extension runs with the developer's rights. In July 2025 the official Amazon Q Developer extension 1.84.0 shipped with malicious code added through a mis-scoped GitHub token; AWS says it failed to run because of a syntax error.

GlassWorm has hit Open VSX in waves since October 2025, and its 2026 variants also install into VS Code, Cursor and Windsurf. Cursor, Windsurf and VSCodium use Open VSX by default.

Check
  • Is the AllowedExtensions policy deployed (VS Code 1.96 or later), seeded from the current inventory? It overrides the user setting. It is not an integrity control: for a local VSIX, Microsoft says it does not verify origin, stop changes to installed files, or limit runtime permissions. Add a private marketplace and file-integrity monitoring of extension folders [inference].
  • Is ExtensionsAutoUpdateDelay set, so a new extension version waits some hours before it installs?
  • Do you need a private marketplace (ExtensionGalleryServiceUrl, or GitHub's private marketplace for Enterprise customers)?
  • Which editors are approved? Forks are not governed by VS Code policies, so block unapproved editors with application control. [inference]
  • Which extensions are installed? [not run here] 
    code --list-extensions --show-versions

Typical findingsNo allowlist, extensions from unknown publishers, forks outside policy.

D04

Secrets and long-lived tokens on the machine

OWASP ASI03 Identity and Privilege Abuse · MCP01 Token Mismanagement

A developer laptop holds SSH keys, Git, cloud and npm tokens, .env files, and now agent tokens and transcripts. Any process running as the user can read unprotected credential files and use credentials exposed through a helper or agent. Infostealers now collect AI agent tokens too (Gen Digital, September 2026).

Sandboxes do not change that by default: Claude Code's sandbox reads ~/.ssh and ~/.aws unless denied, VS Code passes Git and GitHub CLI credentials in, and Dev Containers forward the SSH agent and reuse local Git credentials.

Check
  • Is a Git credential helper set to store? It saves credentials unencrypted in ~/.git-credentials. The command shows every scope, including system. 
    git config --show-origin --get-all credential.helper
  • Are SSH keys protected by more than file permissions? A key in an SSH agent can be used without its file, so control who can reach the agent socket [inference]. Load keys with ssh-add -t (lifetime), -c (confirm each use) and -h (limit destinations; OpenSSH 8.9 or later). [not run here]
  • Are secret files kept out of agent reads, not only edits? Treat four controls separately: read restriction, edit approval, command isolation, and whether the secret is on the machine at all.
    • VS Code: chat.tools.edits.autoApprove with "**/.env": false only gates edits. GitHub's managed permissions.deny with Read(...) rules blocks reads, but only in Copilot Agent Host sessions. sandbox.userPolicy.filesystem.deniedPaths covers processes the agent starts.
    • Claude Code: Read(...) deny rules in permissions.deny block the Read tool and are merged into the sandbox. sandbox.filesystem.denyRead or sandbox.credentials alone covers shell commands only. Read(./.env) matches only the start folder; Read(.env) matches any depth. Add rules for ~/.ssh and cloud credential folders.
    • Codex: [permissions.filesystem] deny_read in requirements.toml, which users cannot weaken. On native Windows it applies to direct file tools, not to shell subprocess reads.
  • Do GitHub and npm tokens expire, and are they narrowly scoped? Can a developer laptop reach production with its own credentials?
  • Are agent config files with tokens watched for change? Research by Mitiga showed an install script planting a hook that rewrote MCP server addresses in ~/.claude.json to capture OAuth tokens.
  • How long do agents keep transcripts? Claude Code: cleanupPeriodDays.

Typical findingsBroad tokens that never expire, the store helper in use, production keys in .env files.

D05

Prompt injection and poisoned instruction files

OWASP ASI01 Agent Goal Hijack

Text the agent reads can redirect it: a web page, issue, README, code comment, file name or MCP tool output. Agents load instruction files such as AGENTS.md and CLAUDE.md as instructions, so these carry more weight.

In October 2026 Forever Security reported a planted AGENTS.md in a customer's Downloads folder that tried to make Codex install a malicious npm package. In testing, Codex followed it in more than 90% of attempts.

Check
  • Do developers start agents only inside a project folder, never in the home folder or Downloads?
  • Are AGENTS.md, CLAUDE.md and other rule files reviewed like code, for example through CODEOWNERS?
  • Are unreviewed repos opened in VS Code restricted mode? It disables agents in VS Code only; CLI agents rely on their own trust prompts.
  • Are there instruction files you did not write? Each command lists files to review. 
    # macOS and Linux
find ~/Downloads ~ -maxdepth 4 \( -name AGENTS.md -o -name CLAUDE.md \) -not -path '*/node_modules/*' 2>/dev/null | sort -u
# Windows PowerShell
Get-ChildItem -Path $HOME -Recurse -Depth 4 -Include AGENTS.md,CLAUDE.md -ErrorAction SilentlyContinue | Select-Object FullName

Typical findingsAgents started from the home folder or Downloads, instruction files changed without review, fetch allowed for any domain.

D06

Untrusted MCP servers, plugins and skills

OWASP ASI04 · MCP03 Tool Poisoning · MCP07 Insufficient Authentication and Authorization · AST01 Malicious Skills

A local MCP server runs as the developer, and its tool descriptions go straight into the model's context. A remote one holds its own tokens, sees what the agent sends and can return prompt injection. ClawHavoc put more than 1,000 malicious skills on ClawHub in early 2026.

In Plugin4Shell (September 2026), Claude Code, Codex and Copilot ran git checkout <SHA> for a pinned plugin without checking the result, so a branch named after the hash could win. It needs control of the plugin's repo, an update that re-pins it, and a Git host that allows hash-named branches.

CSA says automatic updates, then on by default, made it zero-click; Claude Code's docs now leave them off for third-party marketplaces.

Check
  • VS Code: is ChatMCP (chat.mcp.access) limited to the registry, with ChatAllowedMcpServers or a private registry (McpGalleryServiceUrl)? Microsoft's docs and source code disagree on its values [contested], so confirm with Policy Diagnostics. It does not cover MCP servers the Copilot runtime finds on its own.
  • Claude Code: allowedMcpServers with allowManagedMcpServersOnly, and strictKnownMarketplaces for plugins. A list with only URL entries blocks local stdio servers, so list the ones you allow too.
  • Codex: an [mcp_servers.<name>] allowlist in requirements.toml, matched on identity.command (stdio) or identity.url (remote); use the structured command form to pin arguments. An empty mcp_servers table disables all servers. Plugin-bundled servers need plugins.<plugin>.mcp_servers.<server> entries. For plugin sources, set [marketplaces] restrict_to_allowed_sources = true with marketplaces.allowed_sources; bundled and remotely installed workspace plugins have separate controls.
  • Which remote MCP servers are in use, who runs them, and what data and tokens do they receive? Treat each as a supplier. [inference]
  • Do MCP servers use short-lived, narrowly scoped tokens?
  • Do MCP servers you or a supplier run refuse tokens not issued for them? The MCP security guidance forbids token passthrough: forwarding a client's token unchanged to a downstream API. A proxy server with a static client ID for a third-party OAuth service should get consent per client. Source: the draft specification [may be outdated].
  • Do local MCP servers that use HTTP check the Origin header, bind to localhost and require authentication? The MCP specification (2025-06-18) says servers must validate Origin and should bind to localhost and authenticate, to stop DNS rebinding [may be outdated].
  • Are automatic plugin updates set on purpose for each marketplace? Claude Code's defaults differ by marketplace type, so decide whether a new plugin version may install without review.
  • Are agents patched for Plugin4Shell (Claude Code 2.1.179, Codex 0.146.0 or later)?

Typical findingsMCP servers started from any source, broad personal tokens in MCP config, plugins from personal GitHub repos.

D07

No sandbox and open network

OWASP ASI05 · makes exfiltration in ASI01 and ASI03 possible

Claude Code's sandbox is off by default and does not run on native Windows. It covers shell commands only; hooks, local MCP servers and apiKeyHelper run outside it, and the Read, Edit and WebFetch tools follow permission rules instead.

Codex sandboxes commands by default (network off, writes limited to the workspace) but by default leaves reads open. VS Code's agent sandbox leaves network on by default, is experimental on Windows, and is not a virtual machine or user-account boundary. A dev container gets Git credentials and the SSH agent by default.

Check
  • Is sandboxing required centrally? VS Code: ChatAgentSandboxEnabled is deprecated; Microsoft points to the Copilot managed setting sandbox.enabled and calls managed enforcement a preview. Claude Code: sandbox.enabled, failIfUnavailable (refuse to start where the sandbox cannot run, such as native Windows) and allowUnsandboxedCommands: false.
  • What is the effective policy? When the sandbox is admin-required, Claude Code ignores loosening settings from a repository but still honours user settings and --settings, which can add excludedCommands, write paths and socket access [inference]. Lock with allowManagedReadPathsOnly and allowManagedDomainsOnly, and pin enableWeakerNestedSandbox, enableWeakerNetworkIsolation, network.allowAllUnixSockets and network.allowLocalBinding to false [inference].
  • Codex: is danger-full-access blocked in requirements.toml? From Codex 0.138.0 use allowed_permission_profiles with a managed default_permissions; older deployments use allowed_sandbox_modes = ["read-only", "workspace-write"]. Settings in config.toml and managed_config.toml are defaults users can change, not requirements.
  • Is outbound access allowlisted? Claude Code: sandbox.network.allowedDomains with allowManagedDomainsOnly covers shell commands; WebFetch(domain:...) allow rules only pre-approve fetches and are not an allowlist. VS Code: sandbox.userPolicy.network.allowOutbound for commands, ChatAgentNetworkFilter for the fetch tool and integrated browser. Codex: [experimental_network] in requirements.toml for commands, with enabled = true; limited Windows support. Web search, MCP and apps have separate controls.
  • Is an allowed domain still a way out? An allowed service such as github.com can receive data into an attacker's account. Anthropic warns that broad domains create exfiltration paths and that hostname-only filtering without TLS inspection can be bypassed, for example by domain fronting. Keep the list short, and restrict by account, tenant or operation where the service allows it.
  • Which local services can a command reach? Docker and other Unix sockets and unauthenticated localhost services can give a command more power than file and domain rules suggest; Anthropic names these sockets as ways around its sandbox. Keep the Docker socket out of agent sessions, leave sandbox.network.allowAllUnixSockets and allowLocalBinding (macOS) off, and require authentication on local services.
  • On Windows: is there a plan for WSL2 or dev containers? VS Code's Windows sandbox needs Windows 11 25H2 build 26200.9550 or 26H1 build 28000.3086 or later.
  • Is high-risk work, such as unknown repos and autonomous runs, done in a dev container or cloud session with credential forwarding turned off where it is not needed?

Typical findingsSandbox off, network open, a Windows fleet assumed to be sandboxed, autonomous runs on the main laptop.

D08

Approval bypass

OWASP ASI02 Tool Misuse · ASI09 Human-Agent Trust Exploitation

Approval prompts fail when they are switched off (Allow all, Autopilot, bypass modes, or a project file), or when the prompt shows something other than what happens. CVE-2025-53773 let a prompt injection make Copilot write "chat.tools.autoApprove": true into workspace settings.

GhostApproval (Wiz, July 2026) used repo symlinks to make six agents write outside the project, such as to ~/.ssh/authorized_keys; in some, the prompt named a harmless file or came after the write. Anthropic disputed that it is a vulnerability.

Check
  • Is the VS Code policy ChatToolsAutoApprove set to block global auto-approve? It also takes Assisted permissions, Allow all and Autopilot out of use.
  • Do high-risk tools always ask? ChatToolsEligibleForAutoApproval can require approval for named tools, but it does not stop Assisted permissions or approvals saved earlier in a Copilot harness session.
  • Claude Code: are permissions.disableBypassPermissionsMode and, where needed, permissions.disableAutoMode set to "disable" in managed settings? Anthropic's settings reference also accepts disableAutoMode at top level. Check enforcement on the deployed version.
  • Codex: does requirements.toml set allowed_approval_policies = ["on-request"], so --ask-for-approval never is refused? Combine it with the sandbox limit under D07 to block --yolo. Optional command rules in [rules] can force a prompt or forbid matching commands.
  • Codex: on-request does not mean a person decides: with approvals_reviewer = "auto_review" an automatic reviewer can answer. To require a human, set allowed_approvals_reviewers = ["user"] in requirements.toml. This sets who reviews requests, not which actions need approval. [not run here]
  • Copilot: do managed permissions.ask rules cover the actions that must never be approved silently? GitHub says a managed ask rule always needs a fresh approval, which bypass modes, auto-approval, hooks and saved grants cannot satisfy. It applies to Agent Host sessions only.
  • Are approvals granted for the session rather than for the workspace or user?

Typical findingsAllow all used daily to save time, bypass flags in shell aliases, no central policy.

D09

No inventory, version floor or agent telemetry

OWASP MCP08 Lack of Audit and Telemetry · ASI10 Rogue Agents (secondary, detection side)

You cannot act on the next GitSpawn without knowing which agents and versions run where. A Defender process event records the command lines of the new process and its parent, but only the grandparent's name and ID. It does not record the task, prompt, approval or agent session.

Forever Security caught the planted AGENTS.md by watching the agent, not only the user. VS Code ignores a policy value with a syntax error, so policies can fail quietly.

Check
  • Is there an inventory of agents, versions, extensions and MCP servers per machine, for example from Defender for Endpoint and Intune?
  • Is a minimum version enforced? Claude Code: requiredMinimumVersion, set to a current build rather than the first fixed one. Codex permission-profile requirements need 0.138.0 or later, so set the version floor before relying on them.
  • Is managed-settings JSON validated before rollout? A Claude Code managed settings file, plist or HKLM value that is not valid JSON stops Claude Code from starting, and a developer with local admin rights can edit the managed policy itself.
  • Can you see which commands agents started? A first Defender advanced hunting query [not run here]. It matches only events where the initiating process or its parent looks like an agent, so deeper processes and renamed agents are missed. Join on process IDs and creation times to rebuild the chain: 
    DeviceProcessEvents
| where InitiatingProcessCommandLine has_any ("claude", "codex", "copilot")
    or InitiatingProcessParentFileName has_any ("claude", "codex", "copilot")
| project Timestamp, DeviceName, InitiatingProcessParentFileName,
    InitiatingProcessParentId, InitiatingProcessId,
    InitiatingProcessFileName, InitiatingProcessCommandLine, FileName, ProcessCommandLine
  • Does agent telemetry reach the SIEM? VS Code: CopilotOtelEnabled and CopilotOtelEndpoint. Decide whether to capture prompt content (CopilotOtelCaptureContent). VS Code says hooks are not a complete audit trail.
  • Are policies actually applied? In VS Code run Developer: Policy Diagnostics; in Claude Code run /status and look for Enterprise managed settings on the Setting sources line.
  • Does each policy reach every harness? Some do not: ChatMCP misses MCP servers the Copilot runtime finds itself, and ChatToolsEligibleForAutoApproval does not stop Assisted permissions or saved approvals. Test each one with a real session.

Typical findingsNo agent inventory, updates left to each user, telemetry off, hooks treated as a full audit log.

D10

Code and context sent to unapproved AI services

Data governance, not an OWASP attack class

Model requests can include code, files the agent read, terminal output, tool results and sometimes secrets. The risk is where they go: a personal account, a provider without a company agreement, or an own-key model, where VS Code says content filtering is not guaranteed. In July 2026 Grok Build CLI was found uploading whole Git repositories to xAI's storage.

Check
  • Is ChatApprovedAccountOrganizations set to your approved GitHub organisations? It checks the signed-in account's organisation membership, so a personal account that is a member can qualify; it does not require a company-managed identity. * accepts any signed-in GitHub or GHE account, so do not use it to restrict membership.
  • Claude Code: forceLoginMethod and forceLoginOrgUUID in managed settings.
  • Which agents and providers are approved, and is the list enforced on the machine, not only written in a policy? In VS Code the Claude and Codex harnesses are turned off when Copilot enterprise-managed settings apply.
  • Does session sync to GitHub (CopilotSessionSync) fit your data rules?
  • Does the agreement with each approved provider settle retention, use for training, data residency, subprocessors and deletion? Pinning the account is not enough without these terms. [inference]

Typical findingsPersonal subscriptions on work laptops, no list of approved providers, own-key models in use.

Governance

If something got in

Removing a planted instruction file or updating the agent does not undo what already ran. In Forever Security's case Codex first changed its own settings, which then applied to every later Codex session in any project. The order below is my judgement. [inference]

  1. Isolate the device through your endpoint tool before cleaning it, so stolen sessions and any open tunnel stop working from that machine. Keep it powered on and do not wipe it yet.
  2. Preserve evidence before any cleanup or rebuild. Microsoft's incident-response guidance says not to destroy forensic evidence. Copy to storage the user cannot change: agent transcripts (they age out; see Claude Code's cleanupPeriodDays), agent and MCP config, shell history, planted files, package artifacts, and endpoint, code host, cloud and identity logs. [inference] Collect quickly, so revoking access is not delayed.
  3. Revoke tokens and sessions, not only passwords: GitHub, npm, cloud, SSH keys, MCP OAuth tokens and the agents' own sign-in tokens. Forever Security advises assuming the agent login token leaked, since a stolen token works as a live session.
  4. Look for persistence outside the repo: user-level agent config such as ~/.codex/config.toml, ~/.claude/settings.json and MCP addresses in ~/.claude.json, VS Code user settings, user tasks and extensions, global Git config and hooks, shell startup files, and services or scheduled jobs, including a code tunnel service.
  5. Follow the identity downstream: pushes, pull requests, workflow runs, package publishes, and cloud and SaaS sign-ins or changes made with the developer's credentials during the window.
  6. Recover from a known-good state once the evidence is preserved and the scope is clear: rebuild or restore the machine, reissue credentials after the rebuild, and check repos and packages the identity could change.
